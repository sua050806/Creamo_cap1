# 기술적 의사결정 기록 (Decision Log)

프로젝트 진행 중 내린 주요 기술적 선택과 그 이유를 짧게 기록한다. "왜 이 기술/구조를 선택했는지"를
나중에(포트폴리오 정리, 면접 등에서) 다시 설명할 수 있도록 남겨두는 것이 목적이라, 결론뿐 아니라
**어떤 대안을 검토했고 왜 그걸 고르지 않았는지**까지 적는다.

형식: 상태는 `확정` 또는 `결정 필요`(아직 미확정, 다음 논의에서 정할 것).

---

## ADR-001. 백엔드: Django + DRF
**상태**: 확정
사용자·벤더·상품·주문·정산이 서로 강하게 연결된(FK 관계가 많은) 도메인이라, 이런 관계형 데이터와
회원 권한(role 기반 접근 제어)을 다루는 데 Django의 ORM과 인증 시스템이 잘 맞는다고 판단.

## ADR-002. 프론트엔드: Next.js + TypeScript
**상태**: 확정
반응형 웹만 필요(모바일 앱 없음)하고, 페이지 라우팅·SSR 등을 직접 설정하는 대신 Next.js가 기본
제공하는 구조를 활용하는 편이 4주 일정에 유리. TypeScript는 여러 역할(구매자/크리에이터/관리자)별로
API 응답 형태가 다 달라서, 타입으로 구조를 명시해두면 실수를 줄일 수 있다고 판단.

## ADR-003. 비동기 처리: Celery + Redis 도입
**상태**: 확정
정산 배치 계산과 PG 웹훅 처리는 사용자의 즉각적인 응답을 기다리게 하면 안 되는 작업이라 백그라운드로
분리. 대안으로 "그냥 동기로 처리하고 나중에 필요하면 비동기로 바꾼다"도 있었지만, 정산 로직이 3주차에
들어가는 걸 감안해 처음부터 구조를 잡아두는 쪽을 선택.

## ADR-004. 결제: PortOne(PG), 외부 이탈 없는 결제 흐름
**상태**: 확정
국내 PG 중 국내 결제 수단(카드/카카오페이/네이버페이/무통장입금)을 한 번에 지원하고, 벤더/크리에이터
분리 정산(멀티벤더 정산) 관련 문서가 있어 우선 채택. 다만 실제 멀티벤더 정산 API 지원 여부는 3주차
결제 연동 전에 다시 확인 필요.
결제 인증 과정에서 팝업/리다이렉트는 허용하되, 완전히 다른 쇼핑몰로 사용자가 이탈하는 구조(예: 벤더
자체 결제 페이지로 넘기는 방식)는 만들지 않기로 함 — 플랫폼이 결제를 직접 통제해야 정산 로직이 단순해짐.

## ADR-005. User 모델에 역할(role) 필드로 3개 계정 유형 통합, 벤더는 계정 없이 마스터 데이터로
**상태**: 확정
구매자/크리에이터/관리자는 "로그인해서 뭔가를 하는" 공통점이 있어 하나의 User 테이블 + role 필드로
관리. 벤더는 스펙상 시스템에 로그인하지 않고 오프라인으로 정보를 전달하는 존재라, User와 아예 분리된
`VendorProfile` 테이블(로그인 계정 없는 순수 데이터)로 설계. `password_hash`도 별도 필드로 직접 만들지
않고 Django의 `AbstractUser`가 제공하는 비밀번호 해싱 기능을 그대로 사용.

## ADR-006. 가격은 정수형(원 단위, 소수점 없음)
**상태**: 확정
원화는 소수점 단위 결제가 없으므로, 부동소수점 오차 문제를 피하기 위해 `price`, `unit_price`,
`commission_amount`, `total_amount` 등 금액 필드는 모두 정수(원 단위)로 저장.

## ADR-007. OrderItem에 주문 시점 가격/커미션을 스냅샷으로 저장
**상태**: 확정
Product 가격이나 CreatorRecommendation의 커미션율은 나중에 바뀔 수 있는데, 이미 발생한 과거 주문의
금액까지 같이 바뀌면 안 되므로, 주문 생성 시점에 `unit_price`·`commission_amount`를 OrderItem에
복사해서 고정한다.

## ADR-008. CreatorProfile.category — Category FK로 확정
**상태**: 확정 (2026-09-04)
크리에이터의 관심 분야를 상품 카테고리와 같은 `Category` 테이블로 관리하기로 함. 자유 텍스트도 검토했지만
(구현이 더 간단하다는 장점), 같은 체계를 쓰면 "이 카테고리 상품을 추천하는 크리에이터"처럼 카테고리
기준으로 크리에이터·상품을 함께 필터링할 수 있어 채택. `docs/erd.md` 참고.

## ADR-009. Settlement.target_id 다형성 처리
**상태**: 결정 필요
`target_type`+`target_id` 조합 vs Django `GenericForeignKey`. 우선 구현 난이도가 낮은 단순 필드
조합으로 시작하고, 필요해지면 리팩터링하는 쪽으로 가정 중.

## ADR-011. 인증 방식 — 세션 쿠키로 확정
**상태**: 확정 (2026-09-04)
JWT와 비교 검토: JWT는 프론트·백엔드가 여러 클라이언트(웹+모바일)에 API를 공유하거나 서버를 stateless로
확장할 때 유리하지만, 리프레시·무효화 로직을 직접 구현해야 해서 개발량이 늘어남. 크리모는 모바일 앱이
없고 프론트·백엔드가 한 팀·한 배포 단위로 묶여 있어, Django가 기본 제공하는 세션 쿠키 인증으로도 충분하다
고 판단. 세션 쿠키는 서버가 언제든 특정 세션을 강제 무효화할 수 있고(로그아웃 즉시 반영), `httpOnly`
옵션으로 XSS에 의한 탈취 위험도 낮출 수 있음. 대신 CSRF 방어가 필요한데 Django가 기본 제공.

## ADR-012. 커미션율은 관리자가 정함 — Product 기본값 + CreatorRecommendation 개별값
**상태**: 확정 (2026-09-04, 2026-09-04 재검토 후 구조 수정)
크리에이터가 추천 등록 시 직접 커미션율을 입력하게 하는 안도 검토했지만, 과도한 수수료 설정 등 어뷰징
위험이 있고 벤더가 실제로 감당 가능한 수수료율을 정확히 아는 쪽은 관리자·벤더라고 판단해 제외.

처음엔 "고정값"을 "상품 하나당 값 하나(모든 크리에이터 동일)"로 해석해서 `Product.commission_rate`
하나만 두고 `CreatorRecommendation.commission_rate`를 아예 없앴는데, 사용자가 "같은 상품이라도 크리에이
터마다 협상 요율이 다를 수 있지 않냐"고 지적해서 재검토함. 실제로 "누가 정하는가"(크리에이터 vs 관리자)
와 "어느 단위로 값이 존재하는가"(상품당 vs 크리에이터+상품 조합당)는 서로 다른 질문이었음.

최종 구조: `Product.commission_rate`는 관리자가 상품 등록 시 정하는 **기본값**. 크리에이터가 추천을
등록하면 이 기본값이 `CreatorRecommendation.commission_rate`로 **복사**되어 저장되고(크리에이터가 직접
입력하지 않음), 이후 관리자가 특정 크리에이터의 값만 개별적으로 조정할 수 있다 — 조정해도 상품 기본값이나
다른 크리에이터 값에는 영향 없음. `docs/erd.md`, `docs/api-spec.md`의 `POST /creator/recommendations`
참고.

## ADR-013. 장바구니는 서버 DB에 저장 (Cart/CartItem 신설)
**상태**: 확정 (2026-09-04)
스펙 7번 원안은 "장바구니만 React Context나 로컬스토리지로 처리"였으나, 로그인한 사용자가 기기를
바꿔도(예: PC에서 담고 모바일로 결제) 장바구니가 유지되는 게 사용자 경험상 중요하다고 판단해 서버 DB
저장으로 변경. `Cart`(구매자 1인당 1개), `CartItem`(담긴 상품 한 줄) 두 테이블을 새로 추가함 —
스펙 4번 원본 데이터 모델 표에는 없던 엔티티. `docs/erd.md` 참고. 트레이드오프: 로컬 처리보다 백엔드
구현량이 늘어나지만, 3주차에 어차피 결제 연동을 하면서 장바구니 → 주문 흐름을 서버에서 다루게 되므로
추가 부담이 크지 않다고 판단.

## ADR-014. 크리에이터 대시보드 "클릭수" 집계는 이번 스코프 제외
**상태**: 확정 (2026-09-04)
추천 링크 클릭을 집계하려면 클릭 이벤트를 기록하는 별도 테이블과, 모든 상품 상세 페이지에 추적 코드를
붙이는 작업이 필요해 개발량이 늘어남. 판매수·커미션 통계만으로도 대시보드의 핵심 가치(크리에이터가
자신의 추천 성과를 확인하는 것)는 충족되므로, 4주 일정을 고려해 이번 스코프에서는 제외하고 다음 단계
확장 항목으로 남겨둠 → 스펙 9번(향후 확장 계획)에 함께 정리 가능.

## ADR-016. Product.stock — 옵션 조합별 재고로 확정
**상태**: 확정 (2026-09-04)
상품 전체 재고 하나로 관리하는 안(구현 단순)도 검토했지만, 실제로는 "블랙은 품절, 화이트는 재고 있음"
같은 상황이 흔해서 옵션 조합별 재고가 더 정확하다고 판단. 새 테이블을 추가하는 대신, 기존 `options`
필드와 같은 방식으로 `stock`도 JSONB로 바꿔 옵션 조합을 키로 하는 딕셔너리 형태로 저장하기로 함(예:
`{"블랙-S": 10, "화이트-M": 5}`). 별도 테이블보다 구현이 단순하면서도 옵션별 재고를 표현할 수 있음.

## ADR-017. Payment — Order와 1:N(재시도마다 새 레코드)
**상태**: 확정 (2026-09-04)
Order와 1:1로 두고 재시도 시 기존 레코드를 갱신하는 안(구현 단순)도 검토했지만, 결제 실패 이력을 그대로
보존하는 편이 나중에 "왜 결제가 여러 번 실패했는지" 추적하기 쉽고, PG 웹훅 처리 로직에서도 각 시도를
독립된 레코드로 다루는 게 자연스럽다고 판단해 1:N(`ForeignKey`)으로 확정.

## ADR-018. CreatorRecommendation — 동일 크리에이터·상품 중복 추천 불가
**상태**: 확정 (2026-09-04)
한 크리에이터가 같은 상품을 여러 번 추천 등록해야 할 이유가 없어, `unique_together = ("creator",
"product")` DB 제약으로 원천 차단하기로 함.

## ADR-019. Settlement.target_id — 단순 필드 조합(GenericForeignKey 미채택)
**상태**: 확정 (2026-09-04)
`GenericForeignKey`(Django가 여러 테이블 중 하나를 자동으로 가리키게 해주는 고급 기능)도 검토했지만,
정산 기능은 관리자만 다루는 내부 기능이라 데이터 규모나 조회 빈도가 크지 않고, 개념이 더 어려운 기능을
쓸 만큼의 이득이 없다고 판단. `target_type`(문자열) + `target_id`(정수) 조합으로 구현하고, 코드에서
직접 분기 처리하기로 함.

## ADR-020. 장바구니 중복 담기 — 상품+옵션+크리에이터 조합이 같을 때만 수량 증가
**상태**: 확정 (2026-09-04)
단순히 "같은 상품이면 수량만 늘린다"고 하면, 서로 다른 크리에이터의 추천을 통해 같은 상품을 담은 경우
커미션 귀속이 뒤섞이는 문제가 생김. 그래서 상품+옵션+추천 크리에이터가 **모두** 같은 경우에만 기존
`CartItem`의 수량을 늘리고, 셋 중 하나라도 다르면 별도 줄로 추가하기로 확정. `docs/erd.md`
Cart/CartItem 참고.

## ADR-021. 개별 크리에이터 커미션율 조정은 Django 관리자 사이트로 처리 (전용 API 없음)
**상태**: 확정 (2026-09-04)
ADR-012에서 `CreatorRecommendation.commission_rate`를 개별 조정 가능하게 만들었는데, 이걸 위한 전용
화면/API를 따로 만들지 Django가 기본 제공하는 관리자 사이트(모델만 등록하면 자동 생성되는 CRUD 화면)로
충분할지 검토. 이 기능은 자주 쓰이는 일반 사용자 플로우가 아니라 운영진이 가끔 예외적으로 처리하는
작업이라, 4주 일정 안에서는 별도 UI를 만드는 비용이 아깝다고 판단해 Django 관리자 사이트로 충분하다고
결정.

## ADR-022. 벤더 지정 크리에이터는 Django 관리자 사이트에서 대리 등록 + 벤더명 같이 표시
**상태**: 확정 (2026-09-04)
CreatorProfile은 회원가입과 별도 단계로 작성하는 것으로 확정. 여기에 더해 "벤더가 오프라인으로 특정
크리에이터와 협업하기로 정하고, 그 크리에이터의 핸들을 관리자에게 전달하면, 관리자가 그 크리에이터
계정이 실제 플랫폼에 존재/승인되어 있는지 확인한 뒤 대신 추천 등록을 만들어줄 수 있어야 한다"는
요구사항이 나옴.

전용 화면/API를 새로 만드는 대신, ADR-021과 같은 패턴으로 **Django 관리자 사이트**에서
`CreatorRecommendation`을 직접 생성하는 것으로 확정. 크리에이터를 선택하는 필드가 검색 가능한
드롭다운으로 되어 있고, 여기엔 이미 가입·승인된 크리에이터만 표시되므로 — 벤더가 알려준 핸들이 목록에
없으면 "존재하지 않거나 미승인" 상태라는 걸 바로 알 수 있어 별도 검증 로직 없이도 확인이 됨. 여기에
더해, 관리자가 "이 크리에이터가 맞는 벤더 상품을 추천하는 게 맞는지" 한눈에 보기 쉽도록 이 화면의
목록·생성 폼에 연결된 상품의 벤더명도 같이 표시하도록 설정하기로 함(구현은 Django 관리자의
`list_display`에 관련 필드를 추가하는 정도로 간단함).

참고로, 벤더·크리에이터의 신규 가입 신청 자체를 승인/반려하는 통합 목록(`/admin` 프론트엔드 페이지,
`GET/POST /admin/applications`)은 원래 스펙 2.4에 있던 별개 기능이며 이번 논의와는 무관하게 그대로
유지된다.

## ADR-023. (제안, 구현 보류) 벤더 프로필 페이지 — VendorProfile.status를 실제로 의미 있게 만들기
**상태**: 설계만 문서화, 구현은 보류 (2026-09-14)

**문제 발견**: `VendorProfile.status`(승인대기/승인/반려)가 스펙 2.4를 따라 `/admin` 신청 심사 통합
목록에 크리에이터와 나란히 들어가 있는데, 실제로는 **아무 기능도 이 상태값을 확인하지 않음**. 스펙
2.3에는 "플랫폼 화면에는 상품 상세의 '공급 벤더' 배지로만 노출"이라고 되어 있어 벤더 전용 공개 화면
자체가 없기 때문 — 승인해도, 반려해도 화면상 달라지는 게 없어서 승인 절차가 형식적임. 또한 벤더는
크리에이터처럼 스스로 "신청"하는 주체가 아니라 관리자가 오프라인 정보를 받아 대신 등록하는 대상이라,
크리에이터와 같은 "신청 심사" 흐름에 넣는 것 자체가 개념적으로 어색하다는 지적이 나옴.

**제안하는 해결책**: 벤더 전용 공개 페이지(`/vendors/{id}`, 스펙 7번 페이지 목록에는 없던 것 — 크리에이터의
`GET /creators/{id}`와 대응되는 개념)를 새로 만들어서, 그 벤더의 **이름·소개 + 현재 공급 중인 상품
목록**(카테고리 페이지의 상품 카드 그리드와 비슷한 형태)을 보여준다. 이 페이지가 생기면 비로소
`status`가 실제 게이트 역할을 할 수 있음 — 예: 승인된 벤더만 프로필 페이지가 공개되고 그 상품들이
노출됨. 이렇게 되면 벤더도 "심사해서 공개 여부를 결정한다"는 점에서 크리에이터 승인과 같은 선상에
놓이는 게 자연스러워짐.

**필요한 추가 작업** (구현 시):
- `VendorProfile`에 `intro`(소개) 필드 추가 — 현재는 `name`, `business_no`, `contact`,
  `settlement_account`, `status`만 있고 소개글 필드가 없음 (`docs/erd.md` 참고)
- API 추가: `GET /vendors/{id}`(프로필), `GET /vendors/{id}/products`(공급 상품 목록) — 크리에이터
  쪽 API와 대칭 구조
- 프론트엔드: `/vendors/[id]` 페이지, 상품 상세의 "공급 벤더" 배지를 이 페이지로 링크
- `/admin` 신청 심사 화면에서 벤더 처리 방식 재검토(그대로 통합 목록에 둘지, 문구만 "신청"이 아닌
  다른 표현으로 바꿀지는 미정)

지금은 4주 일정상 우선순위가 낮다고 보고 설계만 남겨두고, 실제 구현 여부·시점은 3주차 이후 다시 논의.

**후속 결정(2026-09-14)**: 위 187번째 줄에 남겨뒀던 "`/admin` 신청 심사 화면에서 벤더 처리 방식
재검토" 질문은 ADR-027에서 결론이 남 — 벤더는 통합 목록에서 완전히 빼고 "신청 심사"는 크리에이터만
다루는 것으로 확정.

## ADR-024. 백엔드(Django)도 Docker 컨테이너로 실행 (로컬 venv 직접 실행 폐기)
**상태**: 확정 (2026-09-14)

Windows(한국어 로케일) 환경에서 로컬 Python venv의 `psycopg`가 Docker로 띄운 PostgreSQL에 직접
접속할 때 연결이 계속 깨지는 문제가 발생. `psycopg2`→`psycopg`(v3) 교체, 비밀번호 인증 비활성화
(`POSTGRES_HOST_AUTH_METHOD: trust`), WSL2 재시작까지 시도했지만 동일하게 실패. 결정적으로
PostgreSQL 컨테이너 로그에 연결 시도 자체가 기록되지 않는 것으로 보아, 요청이 서버에 도달하기도
전에 Windows 호스트와 Docker(WSL2) 사이 네트워크 계층에서 데이터가 깨지는 것으로 판단(자세한 진단
과정은 `docs/devlog.md` 2026-09-14 참고).

대안으로 순수 Windows 네이티브 PostgreSQL 설치도 검토했지만, 스펙 3번에 이미 "배포: Docker + AWS"가
명시되어 있어 로컬 개발 환경도 컨테이너 기반으로 맞추는 쪽을 택함 — Django를 Docker 컨테이너 안에서
실행하면 PostgreSQL·Redis와 같은 컨테이너 네트워크로 통신하므로, 문제가 있던 Windows 호스트 경유
구간 자체를 거치지 않게 됨.

`backend/Dockerfile`, `.dockerignore`를 추가하고 `docker-compose.yml`에 `backend` 서비스를 추가.
코드 디렉터리를 볼륨 마운트해서 로컬에서 코드를 수정하면 컨테이너 안에도 바로 반영되고
`runserver`가 자동 재시작하게 함(패키지 추가 시에만 이미지 재빌드 필요). 이제부터 백엔드 명령어는
`docker compose exec backend python manage.py ...` 형태로 실행한다 — 기존 `backend/venv`로 직접
실행하던 방식은 더 이상 쓰지 않음.

## ADR-025. Django 자체 관리자 사이트를 `/django-admin/`으로 이동
**상태**: 확정 (2026-09-14)

`config/urls.py`가 원래 `path('admin/', admin.site.urls)`로 Django가 기본 제공하는 관리자 사이트를
`/admin/`에 물려두고 있었는데, `api-spec.md`에는 우리가 만드는 관리자 콘솔 API가 전부 `/admin/...`
경로(`GET/POST /admin/applications` 등)로 설계돼 있어서 그대로 두면 경로가 충돌한다(`/admin/`으로
시작하는 요청은 전부 Django 관리자 사이트의 URL resolver가 먼저 가로채서, 우리 API가 실제로는 전혀
호출되지 않고 404만 돌려주게 됨).

스펙 문서를 다시 쓰는 대신 Django 기본 관리자 사이트 쪽을 옮기기로 함 — 여기는 원래도 사용자가 직접
들어가는 화면이 아니라, ADR-021·ADR-022처럼 관리자가 `CreatorRecommendation` 등을 수동으로 조정할
때만 가끔 쓰는 보조 화면이라 URL이 바뀌어도 체감상 영향이 없음. `path('django-admin/', admin.site.urls)`로
변경.

## ADR-026. 관리자 콘솔 4개 기능(신청 심사·상품 등록·배송 상태 변경·정산 승인)을 `adminconsole` 앱에 모음
**상태**: 확정 (2026-09-14)

3주차 관리자 콘솔 API를 구현하면서, 기능별로 이미 존재하는 각 앱(`accounts`, `vendors`, `catalog`,
`orders`, `settlements`)에 admin 전용 뷰를 흩어 넣을지, 처음부터 비어 있던 `adminconsole` 앱 하나에
모을지를 정해야 했음. `adminconsole`에 모으는 쪽을 택함 — 관리자 콘솔은 "누가 이 데이터를 갖고
있냐"가 아니라 "관리자가 무엇을 승인/등록/변경하냐"라는 별개의 관심사이고, 실제로 한 화면(`GET
/admin/applications`)이 `CreatorProfile`과 `VendorProfile`처럼 서로 다른 앱의 모델을 한 번에 다루는
경우도 있어서 특정 도메인 앱 하나에 억지로 끼워 넣기 애매했기 때문. `IsAdmin` 권한 클래스
(`adminconsole/permissions.py`, `User.role == "admin"` 체크)도 여기 두고 4개 뷰가 전부 공유한다.

배송 상태 변경(`PATCH /admin/order-items/{id}/status`)과 정산 승인(`GET/POST /admin/settlements`)은
그 대상이 되는 주문·정산 데이터 자체가 아직 하나도 없어서(주문 생성 API, 정산 배치 계산 로직 모두
4주차 스코프) 화면을 확인할 방법이 없었음. 이 두 기능만 나중으로 미루는 대신, 데모/테스트용 주문 1건과
정산 대상 2건을 각각 `orders/migrations/0002_seed_demo_order.py`,
`settlements/migrations/0002_seed_demo_settlements.py`로 시드해서 지금 당장 두 화면 모두 실제
승인/상태변경 동작까지 눈으로 확인할 수 있게 함(이 데이터는 어디까지나 데모용이며, 실제 주문·정산
생성 로직이 붙으면 자연스럽게 실제 데이터로 대체됨).

`GET /admin/order-items`, `GET /admin/vendors`는 `api-spec.md`에 명시돼 있지 않지만 각각 배송 상태
변경 화면의 목록과 상품 등록 화면의 벤더 선택 드롭다운을 채우는 데 필요해서 화면 구현 과정에서
추가함 — `POST /creator/profile`을 문서화 전에 먼저 구현했던 것과 같은 패턴(설계 문서가 구현을
따라가며 채워지는 부분).

## ADR-027. 회원 관리 화면 추가 — User.role을 관리자가 직접 수정 가능하게
**상태**: 확정 (2026-09-14)

관리자 콘솔 4개 기능(ADR-026)을 만든 뒤, "가입한 회원·크리에이터·벤더를 목록으로 확인하고 역할도
바꿀 수 있게 해달라"는 추가 요청이 들어옴. 스펙 7번 페이지 목록에는 없던 화면이지만, 4주 캡스톤이라도
관리자가 잘못 가입된 계정을 고치거나(예: 실수로 buyer로 가입한 사람을 creator로) 테스트 계정 역할을
바꿔볼 수 있어야 한다는 점에서 필요성이 명확해 추가하기로 함.

**설계**:
- `GET /admin/users` — 벤더를 제외한 전체 회원(buyer/creator/admin) 목록. 벤더는 로그인 계정 자체가
  없어서(스펙 2.3) 여기 포함시키지 않고 기존 `GET /admin/vendors`로 따로 조회하게 함 — 두 목록을
  억지로 하나로 합치면 "회원"과 "벤더"라는 서로 다른 개념(계정 유무)이 뒤섞여 오히려 혼란스러워짐.
- `PATCH /admin/users/{id}/role` — `User.role` 필드만 바꾼다. `role`을 creator로 바꿔도
  `CreatorProfile`을 자동으로 만들어주지는 않기로 함 — 크리에이터 프로필 작성(`/creator/apply`)은
  본인이 카테고리·소개 등을 직접 입력해야 하는 별도 단계라, 관리자가 대신 만들어버리면 빈 프로필이
  생기거나 입력값을 관리자가 임의로 채워야 하는 문제가 생김. 그래서 "역할 변경"과 "프로필 작성"을
  분리된 단계로 유지 — 관리자가 role만 creator로 바꿔주면, 그 다음엔 본인이 로그인해서
  `/creator/apply`를 거치는 기존 흐름을 그대로 탄다.
- `GET /admin/vendors`의 응답을 기존 `{id, name}` 두 필드에서 `VendorProfile`의 전체 필드(사업자번호·
  연락처·정산계좌·상태)로 확장 — 상품 등록 화면의 드롭다운은 여전히 `id`/`name`만 쓰지만, 회원 관리
  화면의 벤더 탭에서는 전체 정보를 보여줘야 해서 같은 엔드포인트를 재사용하며 필드를 늘림(따로 API를
  만들 필요 없음).

## ADR-028. 벤더는 "신청 심사" 대상에서 제외 (ADR-023 후속 결정)
**상태**: 확정 (2026-09-14)

ADR-023에서 "벤더 프로필 페이지가 생기기 전까지는 `VendorProfile.status`가 아무 기능도 가리지 않아
승인 절차가 형식적"이라는 문제를 지적하고도 결론은 미뤄뒀었는데, 회원 관리 탭(ADR-027)을 만들며
다시 짚어보니 더 근본적인 문제가 있었음 — **애초에 "심사할 신청"이라는 개념 자체가 벤더에는 성립하지
않는다.** 크리에이터는 본인이 로그인해서 정보를 입력하고 제출하기 때문에 그 시점부터 승인 전까지
"대기 중"이라는 상태가 실제로 존재하지만, 벤더는 로그인 계정이 없어(스펙 2.3) 애초에 본인이 뭔가를
"제출"하는 행위 자체가 없다 — 관리자가 오프라인으로 받은 정보를 스스로 입력해서 `VendorProfile`
레코드를 만드는 것이므로, 그 레코드가 생기는 시점에 이미 관리자의 승인 의사가 반영된 것과 같다.
즉 관리자가 "등록하기로 결정 → 레코드 생성 → (그 다음에) 별도로 또 승인" 순서가 실질적으로 의미
없는 요식 행위였던 것.

**변경 내용**: `GET/POST /admin/applications`(신청 심사)는 크리에이터만 다루도록 되돌림(벤더 케이스
코드 제거). `VendorProfile.status` 필드 자체는 모델에 남겨둠 — 나중에 "이 벤더의 상품 판매를
일시 중단" 같은 활성/비활성 토글 용도로 재활용할 여지가 있고(ADR-023에서 제안한 벤더 프로필
페이지가 생기면 이 값으로 공개 여부를 가릴 수 있음), 지금 당장 필드를 빼는 것보다 "심사 화면에
안 보이게" 하는 쪽이 되돌리기도 쉽고 안전함. 벤더 목록 자체는 회원 관리 탭의 `GET /admin/vendors`에서
계속 확인 가능.

## ADR-029. Product.short_description — 상세 페이지 미리보기용 필드 분리
**상태**: 확정 (2026-09-14)

상품 상세 페이지 상단(가격 바로 아래)에 짧은 미리보기 문구를 두 줄로 잘라서(`line-clamp-2`) 보여주고
있었는데, 이 문구가 하단의 "상세 설명"(`description`, ADR 없음·3주차 API 구현 중 추가된 화면 섹션)과
**같은 텍스트를 그냥 잘라서** 재사용하고 있었음 — 상세 설명은 3~5문장짜리 긴 글로 다시 써놨는데
(2026-09-14 앞선 작업), 그걸 2줄로 자르면 문장 중간에서 뚝 끊기거나 상세 설명과 내용이 겹쳐서
부자연스럽다는 지적을 받음.

`description`(상세 설명, 긴 글)과 `short_description`(목록·상세 미리보기용 한 줄 요약)을 별개
필드로 분리하기로 함. 공교롭게도 `short_description`에 채울 문구는 애초에 0003_seed_products.py에
있던(0005에서 길게 늘리기 전) 원래 한 줄 설명과 내용이 정확히 일치해서, 그 문구를 그대로 재사용해서
채움(`catalog/migrations/0006_product_short_description.py`). 관리자 상품 등록 폼에도 "간단 설명"
입력칸을 추가해서 새로 등록하는 상품도 두 필드를 각각 채울 수 있게 함.

## ADR-030. VendorProfile.status를 "활성/판매중단" 토글로 재정의 + 회원 관리에 벤더별 상품 목록 추가
**상태**: 확정 (2026-09-14)

ADR-028에서 `VendorProfile.status`를 신청 심사 화면에서만 빼놨는데, 그 필드 자체는 여전히
승인대기/승인/반려(신청 심사용 choices)로 남아 있어서 의미가 붕 떠 있었음. ADR-023이 예전에 제안했던
"활성/비활성 토글로 재활용"을 이번에 실제로 구현하기로 함 — 회원 관리 탭에 벤더별 공급 상품 목록을
보여달라는 요청을 처리하다가, 자연스럽게 "이 벤더 상품을 통째로 판매 중단하는 기능도 있으면 좋겠다"는
후속 요청으로 이어짐.

**모델 변경**: `VendorProfile.Status`를 `pending/approved/rejected`(승인대기/승인/반려) 3개에서
`active/suspended`(활성/판매중단) 2개로 바꿈. `pending`이 있을 이유가 없어졌으므로(ADR-028) 아예
choices에서 제거하고, 기본값도 `active`로 바꿔서 관리자가 벤더를 등록하는 순간 바로 정상 노출되게
함(원래 기본값 `pending`이었으면 새로 등록한 벤더 상품이 아무것도 안 보이는 채로 남는 함정이 있었음).
기존 데이터는 `vendors/migrations/0002_vendor_status_active_suspended.py`에서
`pending`/`approved` → `active`, `rejected` → `suspended`로 변환.

**"판매 중단"의 구현 방식**: 개별 `Product.status`를 건드리는 대신(예: 벤더의 상품 9개를 전부
`inactive`로 바꿔버리면, 원래 `sold_out`이었던 상품과 구분이 안 되고 되돌릴 때 원래 상태를 복원하기
까다로움), **조회 시점에 벤더 상태로 필터링**하는 방식을 택함 — `ProductListView`/`ProductDetailView`
(`catalog/views.py`)와 `CreatorProductsView`(`accounts/views.py`, 크리에이터 추천 목록)가 전부
`vendor__status`를 확인해서 판매중단된 벤더의 상품을 걸러낸다. 이렇게 하면 개별 상품 상태를 전혀
건드리지 않고 즉시·안전하게 껐다 켤 수 있고, 되돌릴 때도 완벽하게 원래 상태 그대로 복원됨(별도
백업/복원 로직 불필요).

**API**: `PATCH /admin/vendors/{id}/status`(관리자 콘솔 전용, `{"status": "active"|"suspended"}`)
추가. 회원 관리 탭의 벤더 필터는 표 대신 카드 목록으로 바꿔서, 벤더 하나당 기본 정보 + 활성/판매중단
토글 버튼 + 그 벤더가 공급하는 상품 목록(`GET /admin/products`를 `vendor_id`로 클라이언트에서
그룹핑, 별도 API 안 만듦)을 같이 보여줌.

## ADR-031. 관리자 콘솔에서 상품 이미지 업로드 가능하게
**상태**: 확정 (2026-09-14)

지금까지 상품 이미지(`thumbnail`)는 `MEDIA_ROOT`/`MEDIA_URL` 설정만 해두고, 실제 업로드는 Django
기본 관리자 사이트(`/django-admin/`)에서만 가능했음(ADR-024 이전, 2주차 도입 당시). 우리가 만드는
`/admin` 콘솔에서 상품을 등록·관리하는데 이미지만 다른 화면으로 가야 하는 게 불편하다는 요청으로,
업로드 기능을 `/admin` 안으로 들여옴.

**옵션 검토**: (1) `/admin`에 업로드 기능 추가 (2) 지금 상품들에 placeholder 이미지를 프로그램으로
채워넣기 (3) 사용자가 실제 사진 파일을 전달하면 그걸 넣기. 사용자가 (1)을 선택 — 캡스톤 산출물로
계속 상품을 추가/관리할 거라 매번 Django 관리자 사이트를 오가는 것보다 우리 콘솔 안에서 완결되는 게
낫다고 판단.

**구현**:
- `AdminProductSerializer.thumbnail`을 읽기 전용에서 쓰기 가능(`required=False`)으로 변경.
- `PATCH /admin/products/{id}`(신규, `AdminProductDetailView`) 추가 — 기존 상품의 이미지만 교체/추가할
  때 쓴다. 문서에는 없었지만(원래 GET/POST만 명시) 시드 데이터로 만들어진 8개 상품처럼 이미지 없이
  이미 존재하는 상품에 나중에 이미지를 붙일 방법이 필요해서 추가.
- `POST /admin/products`(등록)도 같은 폼에서 파일을 바로 첨부할 수 있게 함.
- 프론트 `lib/api.ts`의 `apiFetch`가 지금까지 항상 `Content-Type: application/json`을 고정으로
  붙이고 있었는데, 파일 업로드는 `FormData`로 보내야 하고 이때 `Content-Type`은 브라우저가
  boundary까지 포함해서 자동으로 채워야 하므로 우리가 직접 지정하면 깨짐. `options.body`가
  `FormData` 인스턴스인지 감지해서 그 경우에만 `Content-Type` 헤더를 안 붙이도록 수정 — 기존
  JSON 요청 코드는 전혀 안 건드려도 되는 하위호환 변경.
- 상품 등록 폼에 이미지 파일 input 추가(선택), 등록된 상품 목록 각 행에도 썸네일 미리보기 +
  "추가"/"변경" 업로드 컨트롤을 넣어서 기존 상품에도 나중에 이미지를 붙일 수 있게 함.

## ADR-032. 크리에이터 대시보드 실 API 구현 + role별 접근 가드 + 역할별 화면 분리
**상태**: 확정 (2026-09-14)

`/creator/dashboard`가 로그인·역할 확인 없이 아무나 들어가서 볼 수 있고, 내용도
`MOCK_CREATOR_STATUS`라는 상수로 항상 "승인대기"를 하드코딩하고 있던 걸 발견(스펙대로면 크리에이터
승인 상태에 따라 분기해야 하는데 실제로는 아예 분기 자체가 죽어있었음). `/admin`에 이미 적용한
role 가드 패턴(로그인 안 했거나 역할이 안 맞으면 안내만 보여주고 실제 내용은 렌더링 자체를 안 함)을
크리에이터 대시보드에도 적용하고, 김에 실제 API까지 구현하기로 함.

**가드 단계**(`frontend/app/creator/dashboard/page.tsx`): 로딩 중 → 비로그인 → role≠creator →
크리에이터 프로필 미작성 → 미승인(반려 포함) → 승인, 5단계로 나눠서 각 단계에 맞는 화면을 보여줌.
백엔드에서도 `accounts/permissions.py`의 `IsApprovedCreator`(role=creator이고
`CreatorProfile.status=approved`인 본인만 통과)로 API 자체를 막아서, 프론트 가드를 우회해도 실제
데이터는 못 가져가게 함(프론트 가드는 UX용, 백엔드 권한 체크가 진짜 보안이라는 원칙 — `/admin` 때와
동일).

**API 구현**(`accounts/views.py`): `GET /creator/dashboard/stats`, `GET /creator/dashboard/products`
추가. `OrderItem.creator=본인`으로 필터링해서 집계 — `commission_total`(누적 커미션)은
`status="delivered"`인 것만, `commission_pending`(정산 예정액)은 나머지 상태를 합산해서 "이미 확정된
돈"과 "아직 배송 중이라 확정 전인 돈"을 구분함(자세한 필드 의미는 [api-spec.md](api-spec.md) 참고).

**역할별 화면 분리**: "크리에이터/구매자 화면이 달라야 하지 않냐"는 피드백으로 두 곳을 손봄 —
- `Header.tsx`: role=creator일 때만 "크리에이터 대시보드" 링크를 헤더에 추가(구매자용 내비게이션은
  그대로 유지 — admin과 달리 크리에이터도 일반 구매자처럼 카테고리·장바구니를 쓸 일이 있으므로 전부
  들어내지는 않음).
- `mypage/page.tsx`: 지금까지 buyer/creator/admin 전부 같은 카드 레이아웃에 필드 몇 개만 조건부로
  다르게 보여주고 있었는데, 역할별로 레이아웃 자체를 다르게 바꿈. admin은 "관리자 콘솔로 이동" 안내
  카드 하나만(관리자는 헤더에서도 마이페이지 링크가 안 보이지만 URL 직접 접근 대비), buyer는 기존과
  같은 단일 카드, creator는 계정정보 카드 + 크리에이터 활동 카드(핸들·승인상태·대시보드 바로가기)를
  나란히 보여주는 2단 레이아웃으로 분리.

## ADR-033. 장바구니 실 API 구현
**상태**: 확정 (2026-09-14)

스펙에 이미 `Cart`/`CartItem` 모델(ADR-013)과 `GET/POST /cart` 기본 설계(ADR-020: 상품+옵션+
크리에이터 조합이 같으면 수량만 증가)까지 되어 있었지만, `/cart` 프론트 페이지는 제목만 있는 빈
화면이었고 API 자체가 하나도 구현되어 있지 않았음. `orders` 앱(모델은 이미 있었음)에
`CartView`(`GET/POST /cart`), `CartItemView`(`PATCH/DELETE /cart/items/{id}`)를 추가해서 채움.

**응답 형식 보강**: `api-spec.md` 원안은 `product_id`/`creator_id`만 내려주는 형태였는데, 프론트가
장바구니 화면에 상품명·가격·썸네일을 바로 그려야 해서 `product`/`creator`를 중첩 객체로 바꾸고,
`subtotal`(항목별 소계)·`total_amount`(장바구니 총액)를 서버에서 계산해서 같이 내려주도록 확장 —
다른 엔드포인트들에서 반복된 "설계 문서는 최소 형태, 구현하면서 화면에 필요한 필드를 보강" 패턴을
그대로 따름.

**PATCH/DELETE 추가**: 원래 문서는 GET/POST만 있었지만, 실제 장바구니 화면에서 수량 조절·항목 삭제가
당연히 필요해서 `PATCH /cart/items/{id}`(수량 변경), `DELETE /cart/items/{id}`(삭제) 둘 다 구현 중
추가. 둘 다 `cart__buyer=request.user`로 필터링해서 본인 장바구니 항목이 아니면 404 — 다른 사용자의
장바구니 항목 id를 추측해서 건드리는 것을 원천 차단.

**"장바구니 담기" 버튼 연동**: 상품 상세 페이지(`product-actions.tsx`)의 "장바구니 담기" 버튼이
지금까지 "아직 연동 안 됨" 안내 문구만 띄우던 걸 실제 `POST /cart` 호출로 교체. 비로그인 상태면 API
호출 대신 로그인 유도 문구 + 링크를 보여줌. "바로구매" 버튼은 주문/결제 API가 아직 없어서(4주차
스코프) 안내 문구만 그대로 유지.

**범위에서 제외한 것**: 상품 상세 페이지에 "이 크리에이터의 추천으로 담기"를 선택하는 UI가 없어서,
지금은 장바구니에 담을 때 `creator_id`를 항상 비워서 보낸다(추천 링크를 거치지 않고 담은 것과 동일).
크리에이터별 추천 링크 경유 추적(`/products/{id}?creator=핸들` 같은 방식)은 이번 스코프에 없던
기능이라 별도 논의 없이는 손대지 않음 — 커미션 귀속 로직과 직결되는 부분이라 확실한 설계 없이 임의로
구현하지 않기로 함.

## ADR-034. 관리자 콘솔 상품 등록/관리 화면에서 추천 크리에이터 연결 가능하게
**상태**: 확정 (2026-09-14)

"상품 등록할 때 크리에이터 이름을 적어야 그 상품이 크리에이터 프로필에 뜨는 거 아니냐"는 지적을
받고 확인해보니 실제로 그랬음 — `/admin` 콘솔의 "상품 등록"은 `Product` 레코드만 만들 뿐
`CreatorRecommendation`(크리에이터-상품 연결, 상품이 어느 크리에이터의 추천 목록에 뜰지 결정하는
테이블)은 전혀 건드리지 않고 있었음. ADR-021/022에서 "크리에이터 추천 등록은 Django 관리자
사이트에서"라고 확정해뒀던 게 그대로 남아있던 것 — 즉 상품을 우리 `/admin` 콘솔에서 등록한 뒤,
그 상품을 크리에이터와 연결하려면 별도로 Django 관리자 사이트(`/django-admin/`)에 또 들어가야 하는
번거로운 2단계 작업이었음.

**결정**: 이 연결 작업도 우리 `/admin` 콘솔 안에서 끝낼 수 있게 만듦(Django 관리자 사이트 경로가
없어지는 건 아니고, 개별 크리에이터의 커미션율을 세밀하게 조정하는 것처럼 자주 안 쓰는 작업은 여전히
거기서 함 — ADR-021 그대로 유지). 두 가지 진입점을 만듦:
- `POST /admin/products`에 `creator_id`(선택) 필드를 추가 — 벤더가 이미 특정 크리에이터와 협업하기로
  정해서 상품을 등록하는 시점에 미리 알고 있는 경우, 등록과 동시에 연결까지 한 번에 끝냄.
- `POST/DELETE /admin/products/{id}/recommendations` — 등록 시점에 못 정했거나, 나중에 크리에이터를
  추가/교체하고 싶을 때 쓰는 별도 엔드포인트. 이미 등록된 상품(예: 시드 데이터로 만들어져 크리에이터가
  하나도 안 붙어있던 상품들)에도 나중에 자유롭게 연결/해제할 수 있게 하기 위함.

연결 시 `CreatorRecommendation.commission_rate`는 `Product.commission_rate`(기본값)를 그대로
복사한다 — ADR-012의 기존 규칙과 동일. 개별 크리에이터에 대한 우대 요율 조정은 여전히 Django 관리자
사이트에서 처리(변경 없음). 중복 연결(같은 크리에이터를 같은 상품에 두 번)은 `unique_together`
제약(ADR-018)에 걸려서 400으로 막힘.

프론트 상품 등록 폼에 "추천 크리에이터(선택)" 드롭다운을 추가했고, "등록된 상품" 목록에도 "추천
크리에이터" 열을 추가해서 현재 연결 상태를 배지로 보여주고 바로 추가·해제(×)할 수 있게 함.

## ADR-035. 주문 생성 API 구현
**상태**: 확정 (2026-09-14, 결제 연동 전까지는 잠정)

스펙 8번 개발 일정상 "장바구니·결제(PG) 연동"이 3주차(이번 주) 항목으로 명시돼 있어서, 4주차로
미룰 게 아니라 이번 주 안에 끝내야 함 — 지난 devlog에 몇 군데 "4주차 예정"이라고 적어둔 건 스펙을
다시 확인해보니 잘못된 메모였음(정정: 결제 연동도 3주차 스코프). 그중 주문 생성 API부터 구현.

**장바구니와의 관계**: `POST /orders`는 `Cart`/`CartItem`을 전혀 참조하지 않는 독립 API로 확정 —
`items` 배열을 프론트가 직접 넘긴다. 이렇게 하면 "장바구니에서 주문"과 "상품 상세에서 바로구매"가
같은 API를 그대로 재사용할 수 있음(바로구매는 장바구니를 거칠 필요가 없으므로). 대신 장바구니에서
주문한 경우, 주문이 성공한 뒤 프론트가 이미 만들어져 있는 `DELETE /cart/items/{id}`를 항목마다
호출해서 장바구니를 비운다 — 백엔드가 "이 주문이 어느 장바구니 항목에서 왔는지" 추적할 필요가 없어
API가 단순해짐.

**재고 검증·차감**: `Product.stock`은 `{"블랙-S": 10}`처럼 옵션 조합을 키로 하는 JSON(ADR-016)인데,
정작 "옵션 dict를 어떻게 이 키 문자열로 바꾸는가"에 대한 실제 규칙이 코드에 없었음(문서엔 "색상-사이즈
순서 등 규칙을 정해서 고정"이라고만 되어 있었음). `Product.stock_key(option)` 메서드를 추가해서
`options` 필드에 등록된 키 순서대로 값을 `-`로 이어붙이는 것으로 고정(옵션 없으면 `"기본"`). 주문
생성은 DB 트랜잭션(`select_for_update`로 동시 주문 경합 방지) 안에서 재고를 검증·차감하고, 여러
상품 중 하나라도 재고 부족이면 전체 주문을 거부한다(부분 주문 없음).

**커미션 계산**: `creator_id`가 있으면 `CreatorRecommendation.commission_rate`(개별 조정된 값,
ADR-012)를 우선 쓰고 없으면 `Product.commission_rate`로 대체, `creator_id`가 없으면 0.

**남겨둔 문제 — 결제 전 상태 없음**: `OrderItem.Status`가 애초에 `paid`(결제완료)부터 시작해서
"결제 대기" 상태가 없다는 걸 이번에 구현하면서 발견함. 지금은 주문이 생성되는 즉시 `paid`로
시작하는 것으로 임시 확정 — 실제 결제 연동(`POST /payments/request`, 웹훅)을 붙일 때, `paid`
상태로 바로 시작하는 게 맞는지(예: 주문 생성 = 결제창 진입, 결제 성공 시점에 별도 확정 처리가
필요한지) 다시 논의하고 필요하면 `OrderItem.Status`에 상태를 추가하는 마이그레이션을 낼 예정.

## ADR-036. 포트원(PortOne) V2 결제 연동 + 주문 취소·환불 기능
**상태**: 확정 (2026-09-15)

ADR-035에서 남겨둔 "결제 대기 상태 없음" 문제를 실제로 해결하는 단계. 처음엔 취소/환불을 스코프
밖으로 뺐었는데("스펙에 명시 안 돼 있으니까"), 사용자가 강하게 반대함 — 실서비스라면 결제 기능만
있고 취소가 없는 건 말이 안 된다는 지적이 맞아서, 스펙에 없다는 이유만으로 뺀 건 내 판단 실수였고
바로 계획에 다시 포함시켰다. 이 ADR은 결제 연동과 취소 기능을 함께 다룬다.

**PG사 선택과 실제 가입**: 결제대행사로 포트원(구 아임포트) V2를 사용. 테스트 키가 없어서 시뮬레이터로
때울지, 실제로 가입해서 진짜 테스트 연동을 할지 물었고, 사용자가 실제 가입을 선택. 이 과정에서
사용자가 처음 전달한 키(`iamporttest_3`, `test_sk_...`, `test_ck_...`)는 사실 포트원 콘솔에서
"채널"을 설정할 때 입력하는 **토스페이먼츠 채널 단의 키**였고, 실제 연동 코드에 필요한 건 포트원
레벨의 `storeId`/`channelKey`/API Secret이라는 걸 웹 검색으로 확인 → 정확한 값 위치(연동 관리 →
[V2 API] 탭, 채널관리)를 안내해서 올바른 키 세 개를 다시 받음. 이런 대행사 연동은 "가입 대행사"와
"실제 결제망(PG)"이 분리되어 있어서 콘솔 화면만 봐서는 어떤 키가 어느 레벨 것인지 헷갈리기 쉬움.

**아키텍처**: 프론트가 포트원 브라우저 SDK로 결제창을 직접 띄우고(`PortOne.requestPayment`), 결제
성공/실패 응답을 받으면 그 결과를 그대로 믿지 않고 `paymentId`만 백엔드로 넘긴다. 백엔드
(`POST /payments/complete`)는 그 `paymentId`로 포트원 서버 API(`GET /payments/{id}`)를 직접
조회해서 상태가 `PAID`이고 금액이 주문 금액과 일치하는지 재검증한 뒤에만 `OrderItem`을 `paid`로
바꾼다. 프론트에서 온 "성공했다"는 신호를 그대로 신뢰하지 않는 이유는, 클라이언트 응답은 네트워크
조작이나 코드 변조로 위조될 수 있기 때문 — 실제 결제 여부의 유일한 근거는 PG사 자체 서버뿐. 이번
스코프에서는 웹훅(비동기 결제 상태 알림)까지는 만들지 않았는데, 사용자가 결제 버튼을 누른 직후
동기적으로 `/payments/complete`를 호출하는 흐름만 지원하면 충분하고(웹훅은 주로 결제창을 이탈한
뒤 뒤늦게 승인되는 케이스 등을 보완하는 용도), 그 범위에서는 서버 재검증만으로도 위조 결제를 막기에
충분하기 때문.

**OrderItem 상태 흐름 재설계**: ADR-035에서 남겨둔 문제대로, 이제 주문 생성 시 기본값이 `pending`
(결제대기)이고, `/payments/complete`가 검증에 성공해야 `paid`로 바뀐다. 취소는
`pending`/`paid`/`preparing` 상태에서만 가능하고, `shipping`(배송중) 이후로는 막았다 — 이미 물건이
출발한 뒤의 취소는 반품(return) 문제라 성격이 다르고, 이번 스코프에선 반품 플로우는 만들지 않기로
사용자와 합의. 부분 취소(주문 안의 특정 상품만 취소)도 이번엔 지원하지 않고, 주문 전체 단위로만
취소한다 — 상품마다 다른 배송 상태를 가질 수 있는데 그 조합을 다 고려하면 복잡도가 커서, 우선
"주문 전체가 아직 배송 전이면 전체 취소"로 단순화했다.

**재고 복원 — 구현 중 발견한 설계 공백**: 취소 시 재고를 원래대로 되돌리려면 "이 주문 항목이 정확히
어떤 옵션 조합(색상 등)의 재고를 얼마나 차감했는지" 알아야 하는데, `OrderItem`에 옵션 정보를 저장하는
필드가 없었다(장바구니의 `CartItem.option`과 달리). 주문 생성 시점엔 이 정보를 알고 있었지만 저장을
안 해뒀던 것 — 그래서 `OrderItem.option` JSONField를 추가하고, 주문 생성 로직에서 이 값을 함께
저장하도록 고침. 기존에 이미 만들어져 있던 주문 데이터(이 필드 추가 전 생성분)는 `option={}`으로
남는데, 테스트/데모 데이터라 실제 서비스 데이터가 아니므로 그대로 둠.

**결제 취소 = PG 취소 + DB 상태 변경을 한 트랜잭션처럼**: 취소 요청이 오면 먼저 포트원 서버에
`POST /payments/{id}/cancel`을 호출해 실제 결제망에서 취소를 확정하고, 그게 성공해야만 DB에서
`Payment`를 `cancelled`로, 재고를 복원하고, `OrderItem`들을 `cancelled`로 바꾼다(재고 복원과 상태
변경은 `select_for_update`를 쓴 DB 트랜잭션으로 묶어서 동시 요청에 의한 경합을 막음). 포트원 쪽
취소가 실패하면(이미 취소됐거나, 결제 자체가 없거나 등) DB는 아예 건드리지 않고 에러를 그대로
반환 — "PG에서는 취소가 안 됐는데 우리 DB만 취소된 것처럼 보이는" 불일치를 막기 위함.

**프론트엔드에서 발견한 next/script 버그**: 포트원 SDK를 `<script type="module">` 인라인 코드로
불러오면서 Next.js의 `Script` 컴포넌트가 제공하는 `onLoad` 콜백을 썼는데, 실제로는 SDK 로딩은
정상적으로 되는데(브라우저에서 `window.PortOne` 객체가 생김) `onLoad` 콜백 자체가 전혀 호출되지
않는 버그를 Playwright로 디버깅하다가 발견함(공식 문서 어디에도 이 제약이 명시돼 있지 않음).
`onLoad`는 `src` 속성이 있는 외부 스크립트 태그에만 붙는 것으로 추정 — `window.PortOne`이 생겼는지
200ms마다 직접 폴링(`setInterval`)하는 방식으로 우회.

**검증 범위와 한계**: 포트원 SDK 연동, 실제 결제창 렌더링(올바른 상품명·금액 확인), 백엔드 인증
(존재하지 않는 결제 ID 조회 시 401이 아닌 404가 돌아오는 것으로 인증 자체는 성공했음을 확인),
결제 검증/취소 로직은 모두 직접 검증함. 다만 Playwright로 실제 토스페이먼츠 샌드박스 결제창까지
진입해서(카드사 선택 → 신한카드 프로모션 팝업 → 신한 VBV(3D-Secure) iframe → "다른결제" 하위 메뉴)
"결제 성공" 상태까지 끝까지 완료하는 건 시도했으나, 테스트 모드에서도 실제 카드사(신한카드) 인증
UI가 그대로 나오고 "앱없이결제"를 선택하면 휴대폰 인증(실제 SMS/ARS 발송 추정)을 요구해서, 실제
전화번호 없이는 이 마지막 구간을 자동화로 끝까지 통과시키지 못함. 즉 "성공 응답을 받은 뒤의 서버
재검증 로직"은 코드 검토와 실패 케이스(404) 검증으로 확인했지만, 실제 성공 케이스 전체를 엔드투
엔드로 완주하진 못한 상태 — 알려진 한계로 남겨둠.

## ADR-037. 크리에이터 추천 구매 연결 고리 복구 (공개 프로필 페이지 + 추천 관계 검증)

**상태**: 확정 (2026-09-16)

4주차 통합 테스트로 구매자 흐름을 처음부터 끝까지 실제로 눌러보다가, 이 플랫폼의 핵심 전제
("크리에이터가 추천하고 커미션 받는 구조")가 실제 화면에서는 전혀 작동하지 않는다는 걸 발견했다.
상품 상세 페이지엔 "@handle 추천" 배지가 보이는데, 장바구니 담기/바로구매가 백엔드에 보내는 요청
어디에도 `creator_id`가 없었다 — 즉 실제 사용자가 사이트를 정상적으로 눌러서는 어떤 크리에이터에게도
절대 커미션이 붙을 수 없는 상태였다. 지금까지 DB에 있던 "크리에이터 연결된 주문"은 전부 curl이나
테스트 스크립트로 `creator_id`를 직접 넣어 만든 것이었을 뿐, 실사용자 흐름으로는 한 번도 만들어진
적이 없었다.

**원인**: 백엔드엔 크리에이터 공개 API(`GET /creators/{id}`, `GET /creators/{id}/products`)가 이미
구현돼 있었지만, 이걸 보여줄 프론트 페이지(`/creators/[id]`) 자체가 없었다. 크리에이터가 자기 추천
링크를 공유하고, 그 링크로 들어온 사람이 사면 커미션이 붙는 구조가 원래 의도였을 텐데, "그 링크를
만들어서 보여주는 화면"이 통째로 빠져 있었던 것.

**연결 고리 설계**: `/creators/[id]` 공개 프로필 페이지를 새로 만들고, 여기서 상품을 클릭하면
`/products/{id}?creator={creatorId}`로 이동하도록 했다. 상품 상세 페이지(서버 컴포넌트)가 이
`?creator=` 쿼리 파라미터를 읽어서 `ProductActions`(장바구니 담기/바로구매를 담당하는 클라이언트
컴포넌트)에 넘기고, 거기서 `POST /cart`·`POST /orders` 요청 바디에 그대로 실어 보낸다. 홈 화면의
"추천 크리에이터" 섹션 상품 카드와, 상품 상세의 "@handle 추천" 배지도 전부 이 경로로 연결해서
어디서 들어오든 크리에이터 귀속이 끊기지 않게 했다.

**"URL에 `?creator=3`처럼 그대로 노출해도 되냐"는 질문에 대한 답**: 노출 자체는 문제없다 — 쿠팡
파트너스·아마존 어소시에이트 같은 실제 서비스도 평범한 쿼리 파라미터를 그대로 쓴다. 추천 링크는
원래 "누가 봐도 되는" 공개 정보다. 진짜 문제는 이 링크 설계를 만들면서 뒤늦게 발견한 **백엔드 검증
누락**이었다: `POST /cart`는 `creator_id`가 존재하기만 하면(승인 여부조차 확인 안 하고) 받아줬고,
`POST /orders`도 "승인된 크리에이터인지"만 확인할 뿐 "그 크리에이터가 이 상품을 실제로 추천 중인지"는
전혀 확인하지 않았다 — 추천 관계가 없어도 상품 기본 커미션율로 계산해서 그대로 커미션을 붙였다.
즉 승인된 크리에이터 id(추측하기 쉬운 작은 정수)만 알면 전혀 추천한 적 없는 상품의 커미션을 그
크리에이터에게 붙일 수 있는 상태였다. `CartView.post`와 `_resolve_order_item`(`orders/views.py`)을
고쳐서, 이제 `CreatorRecommendation`(그 크리에이터가 그 상품을 실제로 추천 중인지)이 실제로 존재할
때만 크리에이터를 붙이고, 없으면 조용히 무시한다(주문 자체는 그대로 진행, 커미션만 안 붙음 — "존재하지
않는 id"와 "추천 안 한 크리에이터의 id"를 다른 에러로 구분하면 오히려 어떤 id가 유효한지 정보를
흘리게 되므로 둘 다 동일하게 조용히 처리).

**받아들이는 한계**: 이 방식은 "이 사용자가 진짜 그 크리에이터 링크를 거쳐 왔는지"까지는 증명하지
못한다 — 다른 경로로 크리에이터-상품 조합을 알게 된 사람이 URL만 직접 타이핑해서 들어와도 그
크리에이터에게 커미션이 붙는다. 이건 위에서 언급한 실제 어소시에이트 프로그램들도 똑같이 안고 가는
한계(서명된 토큰이나 클릭 로그 추적 없이 "그 링크로 들어와서 산 사람 = 그 크리에이터 덕분"이라고
신뢰하는 구조)라, 4주 캡스톤 스코프에서는 이 이상의 장치(서명 토큰, 클릭 추적 등)는 만들지 않기로
했다. 막아야 하는 건 "관계 없는 크리에이터에게 커미션이 새는 것"이고, 이번 수정으로 그건 막혔다.

**곁가지로 고친 것**: 이 작업을 하며 `CreatorRecommendationProductSerializer`(`GET
/creators/{id}/products`)에 `thumbnail`이 빠져 있어서, 홈 화면 "추천 크리에이터" 섹션의 상품 카드가
항상 회색 그라데이션 플레이스홀더만 보여주고 있었던 것도 같이 발견해서 고쳤다(실제 상품 사진이 있는데도
안 쓰이고 있었음). 같은 김에 이 API의 상품 필터링 기준도 메인 상품 목록(`ProductListView`)과 맞춰서,
판매 중단된 벤더뿐 아니라 품절/비활성 상품도 크리에이터 추천 목록에서 가리도록 했다(원래는 벤더 상태만
확인했음).

## ADR-038. 정산 생성을 Celery 배치 대신 관리자 트리거 동기 처리로 단순화

**상태**: 확정 (2026-09-17)

4주차("통합 테스트·발표 준비") 진입 후 아직 안 끝난 항목을 점검하다가, "정산 승인" 화면에 뜨는
숫자가 전부 개발 초반에 화면 확인용으로 심어둔 가짜 데이터(`settlements/migrations/
0002_seed_demo_settlements.py`)라는 걸 다시 짚었다. 승인 버튼 자체는 정상 동작하지만, 실제 주문
데이터로 정산 금액을 계산하는 로직은 처음부터 "Celery 배치가 미리 만들어둔다"고 가정만 해두고 한
줄도 구현이 안 된 상태였다(`docker-compose.yml`에 Celery 워커 자체가 없음).

**선택지 세 가지를 사용자와 논의**: (1) 스펙 그대로 Celery+Redis로 주기적 자동 배치를 만든다, (2)
관리자가 버튼을 누르면 그 자리에서 실제 데이터로 계산하는 동기 처리로 단순화한다, (3) 지금처럼
데모 데이터로 두고 화면 흐름만 보여준다. 캡스톤 발표에서 중요한 건 "실제 데이터로 정확히 계산되는
걸 보여주는 것"이지 "예약 실행되는 것"은 아니라고 판단해서 (2)를 선택했다. Celery는 (a) 사람이
안 시켜도 자동/주기적으로 돌아야 하거나 (b) 계산이 오래 걸려서 요청-응답 안에 끝내면 안 될 때
필요한 도구인데, 지금 규모(주문 수십~수백 건)에서는 버튼 클릭 한 번의 응답 시간 안에 계산이 충분히
끝나서 둘 다 해당하지 않는다 → 별도 백그라운드 작업 인프라 없이 평범한 API 하나로 처리.

**구현**: `POST /admin/settlements/generate`(관리자 전용) — 배송완료(`delivered`)됐고 아직 어떤
정산에도 포함 안 된 `OrderItem`을 전부 찾아서, 크리에이터별로 `commission_amount` 합계를, 벤더별로
`(단가×수량 − commission_amount)` 합계를 각각 계산해 `Settlement`를 만든다. 정산 대상 기간은
관리자가 따로 고르지 않고 "아직 정산 안 된 배송완료 건 전부, 지금 시점까지"로 단순화했다(월별로
딱딱 끊는 방식이 아니라 미정산분을 그때그때 정리하는 방식).

**중복 정산 방지 — 이번에 발견한 설계 공백**: "버튼을 여러 번 눌러도 같은 주문이 두 번 정산되면 안
된다"는 요구사항을 만족하려면 "이 주문 항목이 이미 어느 정산에 포함됐는지" 추적할 방법이 필요한데,
`OrderItem`에 그런 필드가 없었다. `OrderItem.settled_at`(정산 포함 시각, 기본값 비어있음)을 추가해서,
정산 생성 시 `delivered`이면서 `settled_at`이 비어있는 것만 대상으로 잡고 처리 후 채워 넣는 방식으로
해결. 재고 복원(ADR-036의 `option` 필드 추가)과 같은 패턴 — "나중에야 필요하다는 걸 알게 된 추적용
필드"가 또 한 번 빠져있었던 사례.

curl로 직접 확인: 배송완료 상태인 주문 항목 2개(크리에이터 2건, 벤더 2건)로 정산 4건이 정확한
금액으로 생성되는 것, 버튼을 다시 눌러도 이미 정산된 항목은 다시 잡히지 않아 0건 생성되는 것,
크리에이터 없이(추천 없이 산 경우) 커미션 없이 벤더 몫만 정산되는 것까지 확인.

## ADR-039. 회원가입에 이메일 인증 추가 (Redis 첫 실사용)

**상태**: 확정 (2026-09-17)

사용자 요청으로 회원가입 흐름에 이메일 인증을 추가: 이메일 입력 → 중복확인 → 인증번호 받기 → 코드
입력·확인 → 인증 완료된 상태에서만 나머지 정보 입력 후 가입 가능. 인증 안 된 이메일로는 계정 생성
자체가 막힌다.

**저장소로 Redis를 직접 사용**: `requirements.txt`에 `redis` 패키지와 `docker-compose.yml`의
Redis 컨테이너·연결 정보(`REDIS_HOST`/`REDIS_PORT`)는 이미 있었지만, 실제로 이걸 쓰는 코드는
프로젝트 어디에도 없었다(스펙에서 "Celery+Redis"로 계획했던 정산 배치가 결국 ADR-038에서 동기
처리로 단순화되면서 Redis를 쓸 일이 한 번도 없었음). 이메일 인증코드처럼 "몇 분 뒤 자동으로
없어져야 하는 값"은 Redis의 TTL(만료 시간) 기능과 정확히 맞아떨어지는 용도라, 여기서 Redis를 처음
실사용하기로 함. `django-redis`(Django 캐시 프레임워크와 통합) 대신 `redis` 클라이언트로 직접
연결하는 쪽을 택함 — 캐시 프레임워크의 다른 기능은 전혀 필요 없고 값 저장·조회·만료만 필요해서,
더 단순한 쪽이 낫다고 판단.

`accounts/verification.py`에 관련 로직을 모아둠. Redis 키 3종:
- `email_verify_code:{email}` — 6자리 코드, 5분 TTL
- `email_verify_attempts:{email}` — 틀린 시도 횟수, 코드와 같은 만료 시점
- `email_verified:{email}` — 인증 완료 표시, 30분 TTL(나머지 폼 입력할 시간을 넉넉히 줌)

**API 3개 추가**: `POST /auth/check-email`(중복 확인), `POST /auth/send-verification-code`(코드 발송),
`POST /auth/verify-code`(코드 확인). `POST /auth/signup`은 `SignupSerializer.validate_email`에서
`email_verified:{email}` 키가 있는지 최종 확인 — 인증 절차를 건너뛰고 가입 API를 직접 호출하는 걸
막는 방어선. 가입 성공 후에는 이 키를 지워서(1회용) 재사용을 막는다.

**추가로 넣은 보호장치(사용자와 논의 후 둘 다 포함하기로 결정)**:
- 재발송 쿨다운 60초 — 같은 이메일로 도배성 재요청을 못 하게(Gmail 발송 제한 보호 겸함)
- 틀린 시도 5회 제한 — 6자리 코드는 100만 가지뿐이라 시도 제한이 없으면 자동화된 요청으로 뚫릴 수
  있어서, 5회 틀리면 코드를 무효화하고 재발송을 요구하게 함

**이메일 발송은 Celery 없이 동기 처리**: 코드 발송 요청 하나가 Django `send_mail()`을 그 자리에서
호출해서 SMTP로 바로 보낸다. ADR-038과 같은 판단 — 사람이 누른 요청 하나에 대한 응답이고, 이 규모
에서 SMTP 발송 자체가 오래 걸리는 작업도 아니라 백그라운드 큐가 필요 없음.

**SMTP 자격증명**: 사용자가 채팅에 직접 준 Gmail 계정·앱 비밀번호는 코드에 남기지 않고 루트
`.env`(git 제외)에만 저장, `docker-compose.yml`이 `${EMAIL_HOST_USER}` 형태로 backend 컨테이너에
주입 — 포트원 API Secret(ADR-036) 때와 같은 방식.

**검증**: curl로 중복확인/코드발송/오답시도 카운트/최대시도초과/정답확인/미인증 상태 가입 거부까지
전부 확인. 실제로 사용자 본인 이메일로 진짜 인증 메일을 발송해서(그 계정이 곧 발신 계정이라 자기
자신에게 보내는 안전한 테스트) Redis에 저장된 코드로 가입까지 성공하는 것 확인(테스트 후 계정 삭제).
프론트는 Playwright로 이메일 입력 → 중복확인 → 인증번호 받기 → Redis에서 실제 코드 조회 → 입력 →
확인 → 나머지 필드 입력 → 가입 완료까지 실제 UI로 완주. 중복 이메일이면 "인증번호 받기" 버튼 자체가
안 뜨는 것, 이메일을 다시 바꾸면 인증 상태가 전부 초기화되는 것도 확인.

## ADR-040. 실제 배포 전 마지막 점검에서 발견한 문제들 수정

**상태**: 확정 (2026-09-18)

AWS 배포를 앞두고 "배포하면 안 되거나 문제 있는 부분"을 점검해달라는 요청으로 지금까지 로컬 개발
전용으로만 굴러가던 설정을 훑음. 지금까지 통합 테스트는 전부 "로컬에서 기능이 맞게 동작하는가"만
확인했지, "이 설정 그대로 다른 서버에 올려도 되는가"는 한 번도 점검한 적이 없었어서 실제로 여러 개
발견됨.

**배포하면 바로 막히는 것들**:
- `ALLOWED_HOSTS = []`가 하드코딩돼 있었음 — 배포 가이드가 시키는 대로 `DEBUG=False`로 바꾸는 순간,
  Django가 모든 요청을 400으로 거부하게 됨(빈 `ALLOWED_HOSTS`는 어떤 호스트도 허용 안 함). `CORS_
  ALLOWED_ORIGINS`, `CSRF_TRUSTED_ORIGINS`도 `localhost:3000`으로 하드코딩돼 있어서, 배포된 프론트
  주소에서 오는 요청은 전부 CORS·CSRF로 막힘. 셋 다 환경변수로 읽게 바꾸되, 값이 없으면 기존 로컬
  개발 동작과 똑같이 동작하도록 기본값을 맞춰서(`localhost,127.0.0.1` 등) 로컬 개발 경험은 그대로
  유지.
- `frontend/Dockerfile`이 아직 없었음 — 배포 가이드 초안에 "없으면 만들어달라고 요청"이라고 미리
  적혀 있던 바로 그 상황. 새로 만듦.
- **가장 놓치기 쉬웠던 문제**: Next.js의 `NEXT_PUBLIC_*` 환경변수는 컨테이너 *실행* 시점이 아니라
  `npm run build` *시점*에 결과물(JS 번들)에 그대로 박힌다. 배포 가이드 초안의 `frontend` 서비스
  예시는 `environment:`로 `NEXT_PUBLIC_API_BASE_URL`을 넘기려고 했는데, 이건 컨테이너가 이미 빌드된
  *뒤* 실행 시점에나 적용되는 방식이라 전혀 반영이 안 됨 — 그대로 배포했으면 프론트가 계속
  `localhost:8000`을 호출하려고 시도해서 전부 실패하고, 포트원 결제도 빈 store/channel 키로 시도돼서
  깨지는 상황이었음. `frontend/Dockerfile`에 `ARG`로 받아서 `ENV`로 넘기고, `docker-compose.prod.yml`
  (배포 전용 오버레이 파일, 프론트 컨테이너만 추가)에서 `build.args`로 전달하도록 고침 — 실제로 더미
  값을 넣어 이미지를 빌드하고, 빌드된 `.next` 결과물 안에 그 값이 실제로 박혀 들어간 것까지 직접
  확인. 로컬 개발(`docker-compose.yml` 하나만 사용, 프론트는 `npm run dev`)은 그대로 두고, 배포 시엔
  `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build`로 오버레이 파일을
  같이 사용하는 구조로 분리.

**보안 문제(당장 안 막히지만 위험함)**:
- `SECRET_KEY`가 소스코드에 하드코딩된 채 git에 커밋돼 있었음 — 환경변수로 읽게 바꾸되, 로컬 개발
  기본값은 기존 값 그대로 유지(이미 git 이력에 노출된 값이라 더 숨길 의미가 없음), 배포 시에는
  `.env.example`에 새로 생성하는 방법(`get_random_secret_key()`)을 안내.
- Postgres·Redis가 `POSTGRES_HOST_AUTH_METHOD: trust`(비밀번호 없이 접속 허용) 상태로 호스트 포트
  (`5432`, `6379`)에 그대로 매핑돼 있었음. 배포 가이드의 보안 그룹 설정(22/8000/3000만 허용)을
  정확히 따르면 외부 접속은 막히지만, 애초에 백엔드는 도커 내부망(서비스 이름)으로만 접속하면 되고
  호스트에 포트를 열 필요가 전혀 없어서, 보안 그룹 설정 실수 하나로 비밀번호 없는 DB가 인터넷에
  그대로 열리는 구조 자체를 없앴다(포트 매핑 제거). `trust` 인증 자체는 유지 — 로컬 Windows+한국어
  로케일에서 SCRAM 비밀번호 인증 중 psycopg가 에러 메시지를 깨뜨리는 실제 문제 때문에 필요했던
  설정이고, 포트를 안 여니 실질적 위험은 사라짐.
- Django의 `manage.py check --deploy`를 `DEBUG=False`로 돌려서 추가로 5개 경고(HSTS, SSL 리다이렉트,
  SECRET_KEY 길이, 세션/CSRF 쿠키의 Secure 플래그)를 확인했는데, 전부 "HTTPS를 쓸 때"를 전제로 하는
  경고들이었음. 이 배포 가이드는 도메인·인증서 없이 EC2 퍼블릭 IP를 그대로 쓰는 HTTP 전용 방식이라
  (발표용으로 빠르게 올리는 게 목적, ADR이 아니라 배포 가이드 자체의 스코프 판단), 세션/CSRF 쿠키에
  `Secure` 플래그를 켜면 오히려 HTTP 연결에서 쿠키가 아예 전송이 안 돼서 로그인이 깨진다 — 그래서
  이 5개는 고치지 않고 "HTTPS 없이 배포하기로 한 선택에 따르는 알려진 한계"로 남겨둠. 나중에 도메인
  연결·인증서 발급까지 하게 되면 그때 다시 켜야 함.

**검증**: 컨테이너를 재시작해서 로컬 개발이 그대로 동작하는지(`docker compose exec ... psql`로 DB
확인, Redis 연결 확인, 로그인·전체 페이지 스모크 테스트) 확인. 실제 배포 환경을 흉내 내서 `DEBUG=
False`, `ALLOWED_HOSTS=가짜퍼블릭IP` 등으로 환경변수를 덮어써서 설정이 실제로 바뀌는 것도 직접
확인. `frontend/Dockerfile`을 더미 빌드 인자로 실제로 빌드해서 성공하는 것, 빌드 결과물에 그 값이
박혀 들어간 것까지 확인. 배포 가이드 문서(`Claude outputs/크리모_AWS배포_가이드.md`)도 실제로 만든
구조에 맞게 갱신.

**후속 — 완전히 새로 클론해서 실제로 다 띄워보다가 발견한 추가 문제 2건(2026-09-18 계속)**:
git clone부터 다시 해서(로컬 dev 컨테이너와 포트가 겹치지 않게 임시로 8001/3001에), `.env` 채우고
`docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build` → `migrate` →
`createsuperuser`까지 배포 가이드 그대로 밟아보며 검증하던 중, 코드 검토만으로는 못 찾았을 문제
2개를 실제로 겪으며 발견함:

1. **서버 컴포넌트(SSR) fetch가 배포 환경에서 타임아웃남**: 홈 화면(`/`)처럼 서버 컴포넌트가
   `apiFetchPublic`으로 데이터를 가져오는 페이지들이 컨테이너 안에서 `NEXT_PUBLIC_API_BASE_URL`
   (배포 시엔 EC2 퍼블릭 IP)로 접속을 시도하는데, 이러면 컨테이너가 자기 자신의 퍼블릭 IP로 나갔다가
   다시 들어와야 하는 왕복(hairpin NAT)이 필요해지고, 이게 안 되는 네트워크 환경이면(실제로 로컬
   재현 환경에서 그랬음) 그냥 타임아웃 나서 500 에러. `apiFetchPublic`은 서버 컴포넌트뿐 아니라
   `cart/page.tsx`(클라이언트 컴포넌트)에서도 쓰이고 있어서, 무작정 내부망 주소로 바꿔버리면
   브라우저 쪽 호출이 깨짐 — `typeof window === "undefined"`로 실행 환경을 구분해서, 서버에서
   실행 중일 때만 `INTERNAL_API_BASE_URL`(기본값 `http://backend:8000`, 도커 서비스 이름)을 쓰도록
   `frontend/lib/api.ts` 수정. 이 값은 `NEXT_PUBLIC_*`과 달리 빌드가 아니라 요청 처리 시점에 Node
   서버가 읽는 값이라 `docker-compose.prod.yml`의 `build.args`가 아니라 `environment:`에 넣음.
2. **`backend`라는 이름 자체가 `ALLOWED_HOSTS`에 없었음**: 1번을 고치고 나니, 프론트가 이제
   `http://backend:8000`으로 붙는데 이 요청의 Host 헤더가 "backend"라서 Django가 400으로 거부함
   — 사용자가 `.env`의 `ALLOWED_HOSTS`에 무엇을 넣든 "backend"라는 값은 거기 없을 테니까. "backend"는
   도커 내부망 밖에서는 그 이름으로 접속할 방법 자체가 없어서 무조건 허용해도 안전하다고 판단,
   `ALLOWED_HOSTS`에 사용자 설정과 무관하게 항상 포함되도록 `settings.py`에 고정 추가.

두 문제 다 로컬에서 겉으로 보기엔 멀쩡했던 이유는, 로컬 개발에서는 프론트가 `npm run dev`로 컨테이너
밖(호스트)에서 돌기 때문에 애초에 이 "컨테이너 안에서 컨테이너 밖 주소로 나갔다 들어오는" 상황
자체가 생기지 않아서였음 — 즉 "로컬에서 계속 잘 되던 게 왜 배포 시엔 새로 문제가 생기지" 하는
전형적인 사례. 코드만 읽어서는 발견하기 어려웠고, 실제로 배포 구성 그대로 띄워봐야만 드러나는
종류의 문제라 "완전히 새로 클론해서 끝까지 띄워보는" 이 검증 단계 자체가 값어치를 함. 수정 후
같은 방식으로(새 클론 → `.env` → 두 파일 오버레이 → `migrate` → `createsuperuser`) 처음부터 다시
띄워서, 홈/상품 상세/크리에이터 프로필/장바구니 페이지가 전부 200으로 뜨는 것, 실제 로그인
(CORS + CSRF + 세션 쿠키가 전부 맞물려 동작)까지 되는 것을 확인.

**곁가지 — Docker Desktop 불안정의 진짜 원인 발견**: 이 검증 도중 Docker Desktop이 계속 멈추고
"read-only file system" 에러가 나서 알고 보니 **C 드라이브 용량이 완전히 꽉 차 있었음**(여유 공간
약 1GB). 이번 세션 내내 반복됐던 Docker 관련 불안정 증상들의 진짜 원인이었을 가능성이 높음. 사용자
확인 후 다운로드 폴더의 이미 설치 끝난 설치 파일들(Oracle XE, Flutter SDK, Android Studio, Anaconda,
Docker Desktop 설치본, Eclipse 등 총 9.16GB)을 삭제해서 여유 공간 확보, npm 캐시도 정리. Docker
자체도 이번 검증 과정에서 쌓인 빌드 캐시·이미지를 정리(`docker builder prune`, `docker image
prune`)해서 추가로 5GB 이상 회수.

## ADR-041: 주문에 배송지 입력 추가, 회원 관리 화면에 "신청 전" 상태 구분 (2026-09-18)

실제 배포한 사이트를 써보다가 발견/요청받은 두 가지.

**배송지**: `Order` 모델에 배송지를 저장하는 필드 자체가 없었다 — "배송중"이라는 값은 `OrderItem`의
배송 *상태* 표시용일 뿐, 받는사람/연락처/주소를 입력받는 기능이 통째로 빠져있었음(버그가 아니라
원래부터 없던 기능). 사용자 확인 후 최소 범위로 추가하기로 결정:
- 계정에 저장해서 재사용하지 않고, **주문마다 새로 입력**받아 `Order`에 스냅샷으로 저장(가격
  스냅샷과 같은 이유 — 나중에 주소를 바꿔도 이미 발생한 주문의 배송지는 유지돼야 함). 주소록 관리
  같은 별도 CRUD는 스코프 밖.
- 결제 화면에 통합하지 않고, 장바구니 "주문하기"/상품 상세 "바로구매" 버튼을 누르는 시점에 별도
  모달(`ShippingAddressModal`, 양쪽 공용)로 입력받은 뒤 `POST /orders`에 같이 실어 보낸다 — 결제
  화면(포트원 SDK)은 이미 복잡해서 화면을 더 늘리지 않는 쪽을 택함.
- `recipient_name`/`phone`/`address`는 필수, `address_detail`만 선택. 기존 시드 주문
  (`orders.0002_seed_demo_order`)과의 마이그레이션 호환을 위해 모델 필드 자체는 `blank=True`지만,
  `OrderListCreateView.post`에서 새 주문은 필수로 검증한다.

**회원 관리 "신청 전" 구분**: `GET /admin/users`의 `creator_status`는 원래부터 "크리에이터가 아닌
회원"과 "크리에이터로 가입했지만 `/creator/apply`를 아직 안 거친 회원"을 똑같이 `null`로 내려주고
있었는데, 화면에서도 둘 다 "-"로 보여서 관리자가 구분을 못 하고 있었음. 이게 크리에이터 신청 심사
화면이 계속 비어보이던 것과 연결된 혼란이었을 가능성이 높음(신청서를 실제로 낸 사람이 없으면
`GET /admin/applications`가 빈 목록을 돌려주는 게 정상 동작인데, "신청했는데 안 보인다"고 오해하기
쉬움). API 응답은 안 바꾸고 `members-tab.tsx`에서 `role === "creator"`이면서 `creator_handle`이 없는
경우만 "신청 전" 배지를 추가로 보여주도록 프론트만 수정.

**검증**: 로컬에서 `curl`로 배송지 없이 `POST /orders` 시도해서 400 확인, 배송지 포함해서 주문
생성 → `GET /orders/{id}`에서 그대로 돌아오는 것까지 확인. 프론트 타입체크·전체 페이지 스모크
테스트 통과.

## ADR-042: 상품 삭제 대신 상태(비활성) 전환으로 (2026-09-18)

"상품 삭제는 어떻게 하냐"는 질문에 확인해보니, 삭제 기능 자체가 없었을 뿐 아니라 만들기도 어려운
상황이었음 — `OrderItem.product`가 `on_delete=PROTECT`라서 주문 이력이 하나라도 있는 상품은 DB에서
지우려고 하면 에러가 난다(과거 주문이 가리키던 상품이 사라지면 그 주문 내역도 깨지기 때문에 의도된
제약). `Product.status`에 `inactive`(비활성)가 이미 있었고 `GET /products` 목록도 이미
`status=selling`만 보여주고 있었는데, 정작 관리자 화면에 그 상태를 바꾸는 UI가 없어서 죽은 기능이나
마찬가지였음.

그래서 "삭제" 대신 `PATCH /admin/products/{id}/status`를 새로 추가(`AdminVendorStatusView`와 같은
패턴)하고, 상품 관리 표의 "상태" 칸을 텍스트 표시에서 드롭다운으로 바꿔서 판매중/품절/비활성을
바로 전환할 수 있게 했다. `AdminProductSerializer`가 `status`를 `read_only_fields`로 막아두고 있던
것도(원래 이미지 업로드용 `PATCH /admin/products/{id}`에서 실수로 상태가 바뀌는 걸 막으려던
의도로 보임) 그대로 유지 — 상태 변경은 전용 엔드포인트로만 하도록.

한계: `GET /products/{id}`(상품 상세)는 벤더 상태만 확인하고 상품 자체 `status`는 안 가려서, 비활성
으로 바꿔도 직접 URL로 들어가면 여전히 보인다(목록에만 안 뜸) — 이번엔 안 고치고 알려진 한계로 남김.

**검증**: `curl`로 상태를 `inactive`로 바꾼 뒤 `GET /products` 목록에서 실제로 빠지는 것, 다시
`selling`으로 되돌리는 것까지 확인. 프론트 타입체크·전체 페이지 스모크 테스트 통과.

## ADR-043: 벤더도 본인 계정으로 가입·신청·상품 관리 (2026-09-21)
**상태**: 확정

"크리에이터·구매자처럼 벤더사도 계정을 만들어야 한다"는 요청으로 진행. 교수님 제출 기한(이틀)이
있어서 설계를 먼저 짧게 합의(범위: 상품 관리 + 본인 정산 조회, 가입 방식: 본인 신청 → 관리자 승인,
기존 벤더: 전부 계정 생성해 연결)한 뒤 바로 구현.

**되돌린 결정들**: 벤더는 원래 로그인 계정이 없는 구조로 설계돼 있었음(스펙 2.3, ADR-028에서 "신청
심사" 대상에서도 제외, ADR-030에서 `VendorProfile.status`를 승인대기/승인/반려에서 활성/판매중단
2개로 축소). 이번 요청으로 이 결정들을 상당 부분 되돌림:
- `User.Role`에 `vendor` 추가, `VendorProfile.user`(nullable OneToOne) 신설 — 관리자가 대신 등록한
  레거시 벤더는 계정 연결 전까지 `user`가 비어있음.
- `VendorProfile.status`에 `pending`/`rejected`를 다시 추가(4개: pending/active/suspended/rejected).
  본인 계정으로 신청한 벤더는 `pending`으로 시작해 크리에이터와 같은 승인 흐름을 거치고, 관리자가
  대신 등록하는 레거시 벤더는 여전히 승인 절차 없이 바로 `active`(뷰에서 직접 지정, 모델 기본값과
  무관).
- `GET/POST /admin/applications`(신청 심사)에 벤더도 다시 포함 — 단 `user`가 있는(본인이 실제로
  신청한) VendorProfile만, 레거시 벤더는 "신청"한 적이 없으므로 제외.

**새 API**: `POST /vendor/profile`(신청, `CreatorProfileCreateView`와 같은 패턴), `GET/POST
/vendor/products` + `PATCH .../{id}` + `PATCH .../{id}/status`(본인 상품만 스코프, `IsApprovedVendor`
권한 — `AdminProductsView` 계열과 같은 시리얼라이저 필드에서 `vendor_id`만 빼고 서버가 강제 지정),
`GET /vendor/settlements`(`adminconsole.AdminSettlementSerializer` 재사용, `target_type=vendor &
target_id=본인`으로 필터). 프론트는 `/vendor/apply`, `/vendor/dashboard`를 크리에이터 쪽
(`/creator/apply`, `/creator/dashboard`)과 같은 구조로 신설, 회원가입 폼에 "벤더" 선택지 추가.

**기존 벤더 마이그레이션**: 이미 등록된 벤더 3곳은 실제 이메일이 없는 데이터(회사명·연락처만 존재)라
자동으로 진짜 이메일을 알아낼 방법이 없음 — `backfill_vendor_accounts` 관리 명령으로
`vendor{id}@creamo.local` / 고정 비밀번호(`vendor1234`) 형태의 데모용 계정을 일괄 생성해 연결하는
방식으로 처리. 실제 서비스라면 벤더에게 이메일로 초대 링크를 보내는 식이어야 하지만, 캡스톤 발표
시연 목적으로는 이 방식이 충분하다고 판단.

**구현 중 발견한 버그**: `GET /admin/applications`가 크리에이터·벤더를 한 배열로 합쳐서 내려주는데,
프론트(`applications-tab.tsx`)가 `key={app.id}`만 쓰고 있어서 크리에이터 3번과 벤더 3번처럼 `type`이
다른데 `id`가 겹치는 경우 React key 충돌이 났고, 승인/반려 처리 시 로컬 상태 갱신도 `id`만으로
매칭해서 **엉뚱한 행이 같이 바뀌는** 문제가 있었음(실제로 브라우저에서 재현해서 발견 — curl로
백엔드만 테스트할 땐 안 드러나는 종류의 버그). `key`와 매칭 로직 모두 `type`+`id` 조합으로 수정.

**한계**: 벤더 공개 프로필 페이지(`GET /vendors/{id}` 같은, 크리에이터의 `GET /creators/{id}`에
대응)는 이번 스코프에 안 넣음 — ADR-023에서 제안됐던 것 그대로 구현 보류 상태 유지. 이번에 만든 건
로그인한 벤더 "본인" 전용 API들뿐.

**검증**: 신규 가입 → 신청(pending, 상품/정산 API 403 확인) → 관리자 승인(active) → 상품 등록/상태
변경/정산 조회까지 curl로 전 과정 확인. 다른 벤더 상품 접근 시도가 404로 막히는 것도 확인. 레거시
벤더 3곳 백필 스크립트 실행 → 로그인 → 기존 상품 조회까지 확인. 브라우저(Playwright)로 관리자
콘솔의 "신청 심사"·"회원 관리" 탭을 실제로 클릭하며 콘솔 에러 확인 — 이 과정에서 위 React key 버그를
발견해서 같이 수정. 프론트 타입체크·전체 페이지 스모크 테스트(신설 페이지 2개 포함) 통과.

## ADR-044: 배송 상태 변경도 벤더 본인이 (2026-09-21)
**상태**: 확정

ADR-043 직후 "벤더가 배송 관리도 해야 하는 거 아니냐"는 후속 요청. 맞는 지적이었음 — 상품준비/배송중/
배송완료로 넘기는 `OrderItem.status` 변경이 지금까지 전부 관리자 전용(`AdminOrderItemsView`/
`AdminOrderItemStatusView`, `admin/shipping-tab.tsx`)이었는데, 실제로 상품을 포장·발송하는 건
벤더이므로 벤더가 직접 하는 게 맞다.

`GET /vendor/order-items`, `PATCH /vendor/order-items/{id}/status` 신설 — 기존 관리자용 코드
(`AdminOrderItemSerializer` 재사용, `admin/shipping-tab.tsx`의 `EDITABLE_STATUSES` 기준 그대로
가져옴)를 본인 상품(`product__vendor=본인`)으로 스코프만 좁힌 것. 결제대기(pending)·취소됨(cancelled)
상태는 관리자용과 똑같이 여기서 못 바꾼다 — 결제 확인은 `/payments/complete`, 취소는
`/orders/{id}/cancel`을 거쳐야 재고·결제 상태와 어긋나지 않기 때문. 관리자의 기존 배송 관리 기능은
그대로 유지(레거시 벤더처럼 계정이 없는 경우의 백업 경로로 남겨둠).

프론트는 `/vendor/dashboard`에 "배송 관리" 표를 추가(상품 등록 폼과 정산 내역 사이) —
`admin/shipping-tab.tsx`와 같은 구조.

**검증**: curl로 결제대기/취소됨 항목은 400으로 막히는 것, 결제완료→상품준비 전환 성공, 다른 벤더의
주문 항목 접근 시 404로 막히는 것까지 확인. Playwright로 벤더 계정 로그인 후 대시보드에 "배송 관리"
섹션이 콘솔 에러 없이 뜨는 것 확인. 프론트 타입체크·전체 페이지 스모크 테스트 통과.

## ADR-045: 배송지 입력을 모달 대신 별도 주문 확인 페이지로, 주소는 다음 우편번호 검색으로 (2026-09-21)
**상태**: 확정

ADR-041에서 만든 `ShippingAddressModal`(장바구니/상품 상세에 겹쳐 뜨는 모달, 주소는 그냥 텍스트
입력칸)이 부족하다는 지적 — "주문 페이지를 더 제대로 만들어야 할 듯, 주소도 제대로 넣을 수 있게".
합의한 방향: (1) 모달 대신 `/checkout`이라는 별도 페이지로 분리해서 주문상품 요약·배송지 입력·
결제금액을 한 화면에서 보여주기, (2) 주소는 자유 텍스트 대신 **다음(Daum) 우편번호 검색** 위젯으로
받기(한국 이커머스 표준 방식 — 정확한 주소·우편번호를 보장하고 오타를 줄임).

**구현**: `/checkout` 페이지 신설 — 쿼리 파라미터 유무로 두 경로를 구분한다. 장바구니 "주문하기"는
파라미터 없이 이동해서 `GET /cart`로 항목을 채우고, 상품 상세 "바로구매"는
`?product_id=&quantity=&option=&creator=`로 단일 상품 정보를 실어 보내고 `GET /products/{id}`
(공개 API)로 상세를 채운다. 다음 우편번호 SDK(`t1.daumcdn.net/.../postcode.v2.js`)를 `next/script`로
불러오고, "우편번호 검색" 버튼을 누르면 `new daum.Postcode({oncomplete}).open()`으로 팝업을 띄운다 —
완료 콜백에서 받은 우편번호·도로명주소를 채우고, 상세주소(동/호수 등)만 직접 입력받는다. 우편번호
전용 컬럼은 새로 안 만들고(스코프·시간 고려) `(12345) 서울시 강남구 테헤란로 1`처럼 기존
`address` 문자열 앞에 붙여서 보낸다 — 백엔드 변경 없음.

이 페이지 하나가 장바구니·바로구매 양쪽의 종착점이 되면서, 기존에 양쪽에 각자 있던 주문 생성 로직
(`handleCheckout`, `submitBuyNow`)과 `ShippingAddressModal`을 전부 걷어냄 — `cart/page.tsx`는 이제
"주문하기"를 누르면 `/checkout`으로 보내기만 하고, `product-actions.tsx`의 "바로구매"도 상품 정보를
쿼리 파라미터로 실어 보내기만 한다. 실제 결제(포트원 SDK)는 여전히 기존처럼 주문 생성 후
`/orders/{id}`에서 진행 — 결제 재시도 같은 기존 흐름을 그대로 쓰기 위해 일부러 합치지 않음.

**검증**: Playwright로 (1) 상품 상세 "바로구매" → `/checkout?product_id=...`로 정상 이동, 주문상품
요약·배송지 섹션 렌더링, 배송지 없이 제출 시 검증 에러 확인 (2) 장바구니 "주문하기" → `/checkout`
(파라미터 없이)으로 이동, 요약·결제금액 렌더링 확인 (3) 다음 우편번호 스크립트가 실제로 로드되고
(`window.daum` 객체 존재, CDN 직접 요청도 200) 버튼 클릭 시 에러 없이 동작하는 것 확인 — 팝업 자체는
새 창으로 뜨는 게 다음 위젯의 기본 동작이라 같은 페이지 안 iframe으로는 안 잡힘(정상). 프론트
타입체크·전체 페이지 스모크 테스트(신설 페이지 포함) 통과.

## ADR-046: 배송지 필수를 DB 제약조건으로 강제 (2026-09-22)
**상태**: 확정

"주소나 전화번호에 빈 값이면 안 되게 무결성을 지켜야 한다"는 요청. ADR-041에서 `recipient_name`/
`phone`/`address`를 뷰(`OrderListCreateView.post`)에서만 검증하고 있었는데, 이러면 그 뷰를 거치지
않는 다른 경로(장고 관리자 사이트 `/django-admin/`, `manage.py shell`, 나중에 추가될 다른 코드
경로)로는 여전히 빈 값으로 `Order`가 만들어질 수 있는 구멍이 있었음 — 애플리케이션 코드 하나의
검증에만 의존하는 건 "진짜 무결성"이 아니라는 지적이 맞음.

**변경**: `Order` 모델에 `models.CheckConstraint`를 추가해서 `recipient_name`/`phone`/`address`가
빈 문자열이면 DB 자체가 저장을 거부하게 함(`address_detail`만 선택 정보라 제외). 필드의
`blank=True, default=""`도 제거해서 장고 폼 레벨에서도 필수로 취급되게 함. `manage.py shell`에서
직접 `Order.objects.create(recipient_name="", ...)`를 시도해서 `IntegrityError`로 막히는 것까지
확인 — 뷰를 우회해도 절대 못 만든다.

**기존 데이터**: 이 제약을 걸려면 이미 빈 값으로 있던 기존 주문(ADR-041 이전 테스트/시드 데이터,
19건)을 먼저 정리해야 했음 — 실제 배송지가 있는 진짜 주문이 아니라 개발 중 만들어진 테스트 데이터라
전부 삭제(사용자 확인 후 진행, `OrderItem`/`Payment`는 `on_delete=CASCADE`라 같이 정리됨). 배송지가
채워진 주문 1건만 남음.

**검증**: 마이그레이션 적용 전 위반 데이터 삭제 → 마이그레이션 정상 적용 확인. `manage.py shell`로
빈 값 저장 시도가 `IntegrityError`로 막히는 것 확인. `manage.py check` 통과, 전체 페이지 스모크
테스트 통과.

## ADR-047: 전화번호 형식 검증 (2026-09-22)
**상태**: 확정

ADR-046 직후 "전화번호에 'dd · dd'가 들어가는데 이걸 승인한다고?"라는 지적 — 맞는 말이었음.
ADR-046에서 막은 건 "비어있지 않음"까지였지, "진짜 전화번호처럼 생겼는지"는 전혀 확인하지 않고
있었음. 같은 원칙(애플리케이션 코드 한 곳의 검증만으론 부족, DB가 진짜로 보장해야 함)을 그대로
적용해서 3단계 모두에 정규식 검증을 추가:

1. **DB**: `Order.Meta.constraints`에 `order_phone_format` CheckConstraint 추가 —
   `^0\d{1,2}-?\d{3,4}-?\d{4}$` (010-1234-5678처럼 하이픈 있어도/없어도 되고, 지역번호까지 포괄).
   이 뷰를 거치지 않는 어떤 경로로도 형식이 안 맞으면 저장 자체가 막힘.
2. **뷰**: `OrderListCreateView.post`에서 같은 정규식으로 먼저 검증 — DB 제약에만 맡기면 사용자가
   원인 불명의 500/DB 에러만 보게 되므로, 여기서 먼저 걸러서 친절한 메시지("전화번호 형식이
   올바르지 않습니다. 예: 010-1234-5678")를 보여줌.
3. **프론트**: `/checkout` 제출 전에도 같은 정규식으로 확인 — 서버 왕복 없이 즉시 피드백.

세 군데(모델 `RegexValidator`+DB `CheckConstraint`, 뷰의 `_PHONE_RE`, 프론트의 `PHONE_PATTERN`)가
전부 정확히 같은 정규식을 쓰고 있으므로, 나중에 형식을 바꿀 일이 있으면 세 곳 다 같이 고쳐야 함 —
주석에 서로를 참조하도록 남겨둠.

**검증**: `manage.py shell`로 `phone="dd · dd"`가 DB `IntegrityError`로 막히는 것 확인. `curl`로
같은 값을 뷰에 보내면 500이 아니라 400 + 친절한 메시지로 막히는 것, 정상 형식(`010-9999-8888`)은
그대로 주문이 생성되는 것 확인. 이 작업 중 백엔드 컨테이너의 자동 재시작(`runserver` 파일 감시)이
새 코드를 못 읽어서 `NameError`가 났던 것도 발견 — 컨테이너 재시작 후 재확인해서 해결(코드 버그는
아니었음). `npm run build`(프로덕션 빌드, ADR-045 후속 교훈 적용)까지 통과 확인 후 배포 안내.

## ADR-048: 벤더 계정 필수화로 관리자·벤더 콘솔 중복 제거, 주문번호 표시 정리 (2026-09-22)
**상태**: 확정

마이페이지 주문번호가 DB id를 그대로 노출("#10", "#8" — 테스트 데이터 지우고 나니 번호가 듬성듬성해
보임)하는 것과, 관리자 콘솔·벤더 대시보드에 겹치는 기능이 있다는 두 가지 지적을 한 번에 정리.

**주문번호 표시**: `lib/api.ts`에 `formatOrderNumber(id, createdAt)` 추가 — `#{YYYYMMDD}-{id를 4자리로
0패딩}` 형태(예: `#20260918-0021`)로 화면에만 다르게 보여준다. `Order.id` 자체나 DB는 전혀 안 바꿈,
순수 표시 전용 포맷팅이라 위험이 없음. `mypage/page.tsx`(주문 내역 목록), `orders/[id]/page.tsx`
(주문 상세)에 적용.

**관리자·벤더 콘솔 중복 제거**: ADR-043/044에서 벤더 본인 계정으로 상품·배송을 관리하게 만들면서도,
관리자 콘솔의 "상품 등록"·"배송 상태 변경" 기능은 레거시 벤더(계정 없음)를 위한 백업 경로로 일부러
남겨뒀었다. 이제 두 가지를 확정:

1. **벤더는 계정 없이 존재할 수 없게 함**: `VendorProfile.user`를 nullable에서 필수로 전환(DB
   제약) — `backfill_vendor_accounts`로 기존 벤더 전부 계정을 연결해뒀으므로 안전하게 전환 가능했음.
   이제 관리자 사이트에서도 벤더를 계정 없이 등록할 방법이 아예 없다(장고 폼이 자동으로 필수 처리).
   "레거시 벤더를 위한 백업 경로"라는 전제 자체가 사라짐.
2. **관리자 콘솔에서 "상품 등록" 탭 삭제**: 벤더 본인이 `/vendor/products`로 직접 하므로 관리자가
   대신 할 이유가 없어짐. `AdminProductsView` 등 백엔드 뷰·API 자체는 지우지 않고 남겨둠(디버깅·
   예외 상황 대응용, `IsAdmin` 권한 그대로 유지) — UI에서만 뺐다.
3. **"배송 상태 변경" → "결제 관리"로 범위 축소**: `AdminOrderItemStatusView`가 이제
   `pending`/`paid` 사이만 바꿀 수 있고(현재 상태가 이 둘이 아니면 400), 상품준비 이후 단계는 아예
   손 못 댐 — 그건 벤더 본인 전용(`PATCH /vendor/order-items/{id}/status`, ADR-044). 탭 이름도
   실제 하는 일에 맞게 "결제 관리"로 바꿈. 관리자가 결제 확인·정정이 필요한 상황(예: PG 웹훅 실패)에
   쓰는 도구로 좁혀짐.

**검증**: `manage.py shell`로 계정 없는 `VendorProfile.objects.create()` 시도가
`IntegrityError`(`null value in column "user_id"`)로 막히는 것 확인. curl로 관리자가 결제대기→
결제완료는 바꿀 수 있고 결제완료→상품준비는 막히는 것, 벤더가 상품준비로 옮긴 뒤에는 관리자가 그
항목을 더 이상 못 건드리는 것(400)까지 전체 흐름 확인. Playwright로 관리자 콘솔에 "상품 등록" 탭이
안 보이고 "결제 관리" 탭의 상태 드롭다운이 결제대기/결제완료만 있는 것, 실제 구매자 계정으로 로그인해
마이페이지·주문 상세 양쪽에 새 주문번호 포맷이 뜨는 것 확인. `npm run build` 통과.

## ADR-049: 고객용 크리에이터 검색 페이지 신설 (2026-09-22)
**상태**: 확정

"크리에이터/벤더 검색기능 추가" 요청 — 어디에 필요한지 확인해보니 관리자 콘솔이 아니라 **구매자가
크리에이터를 찾아보는 화면**이었음(벤더는 보통 고객에게 직접 노출 안 하는 대상이라 이 경우엔
크리에이터만 해당). 지금까지 크리에이터를 볼 수 있는 곳이 홈 화면의 "추천 크리에이터" 캐러셀(일부만,
검색 불가)뿐이라 전체를 찾아볼 방법이 아예 없었음.

**구현**: `/creators` 페이지 신설 — 핸들 검색창 + 카테고리 드롭다운으로 승인된 크리에이터 전체를
찾아볼 수 있음. `GET /creators`에 `q`(핸들 부분 일치, `icontains`), `category_id` 쿼리 파라미터
지원을 추가(`CreatorListView.get_queryset()` 오버라이드) — 기존 무파라미터 호출(홈 화면 등)은 그대로
전체 목록을 받으므로 하위 호환됨. 검색은 입력할 때마다 300ms 디바운스 후 서버에 다시 요청(카테고리
목록은 `GET /categories` 재사용). 헤더 내비게이션에 "크리에이터" 링크 추가.

벤더 공개 탐색 페이지는 이번 스코프에 포함 안 함 — ADR-023에서 제안됐던 벤더 공개 프로필과 같은
이유로 구현 보류 상태 유지(이 플랫폼에서 벤더는 상품 공급자일 뿐, 구매자가 벤더 자체를 찾아볼
이유가 크리에이터만큼 크지 않다고 판단).

**검증**: Playwright로 초기 목록에 기존 크리에이터가 보이는 것, 존재하지 않는 핸들 검색 시 빈
상태 메시지가 뜨는 것, 실제 핸들 일부로 검색하면 정확히 찾아지는 것, 헤더의 "크리에이터" 링크가
`/creators`로 이동하는 것 확인. `npm run build` 통과(신설 페이지가 정적으로 프리렌더링됨 확인).
