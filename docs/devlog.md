## 2026-09-04 (1주차) — 프로젝트 착수, 설계 문서화

- 프로젝트 스펙(`크리모_프로젝트_스펙.md`)을 저장소에 반영.
- 개발 환경 확인: Git 2.52, Python 3.11.8, Node.js 22.18, npm 10.9.3 설치 확인. **Docker는 아직
  미설치** — 로컬 PostgreSQL/Redis 실행 및 배포 단계 전에 설치 필요.
- 데이터 모델을 ERD 수준으로 구체화(`docs/erd.md`)하고, API 요청/응답 형식을 상세화(`docs/api-spec.md`).
  이 과정에서 스펙만으로는 확정할 수 없는 결정 사항 여러 개를 발견해 `docs/decisions.md`에
  "결정 필요" 상태로 정리해둠 (예: 크리에이터 카테고리 체계, 인증 방식, 클릭수 집계 여부 등).
- 이어서 "결정 필요" 항목 중 5개를 확정: ① 크리에이터 카테고리는 Category FK ② 인증은 세션 쿠키
  ③ 커미션율은 관리자/벤더가 상품 등록 시 정하는 고정값(크리에이터 직접 입력 불가) ④ 장바구니는 서버
  DB 저장 ⑤ 크리에이터 대시보드 클릭수 집계는 이번 스코프 제외. 근거는 `docs/decisions.md`
  ADR-008, 011~014 참고.
- 위 결정 중 ③·④는 스키마에 실제 영향을 줘서 반영: `CreatorRecommendation.commission_rate` 필드 제거
  하고 `Product.commission_rate`로 이동, `Cart`/`CartItem` 테이블 신설(스펙 원안엔 없던 엔티티 — 스펙
  7번의 "장바구니는 로컬스토리지" 방침과 달라진 부분이니 유의).
- **설계 재검토**: 커미션율 결정 구조를 다시 짚음. 처음엔 "관리자가 고정값을 정한다"는 결정을
  `Product.commission_rate` 하나만 두는 것으로 스키마에 옮겼는데, "같은 상품도 크리에이터마다 협상 요율이
  다를 수 있지 않냐"는 지적을 받고 재검토. "누가 정하는가"와 "어느 단위로 값이 존재하는가"가 서로 다른
  축의 질문이라는 걸 놓쳤던 것 — Product에 기본값을 두고, 크리에이터가 추천 등록 시 그 값이
  `CreatorRecommendation`에 복사되어 개별 조정 가능한 구조로 수정. 근거는 `docs/decisions.md` ADR-012
  참고. (포트폴리오 메모: 설계 결정을 문서화해두니 "왜 이렇게 바뀌었는지"까지 남길 수 있었음 — 이런
  재검토 과정 자체가 나중에 면접 등에서 설계 트레이드오프를 설명할 좋은 소재가 됨.)
- 개별 크리에이터 커미션율 조정은 전용 API 없이 Django 관리자 사이트로 처리하기로 확정
  (`docs/decisions.md` ADR-021) — 자주 쓰는 사용자 플로우가 아니라 운영진이 가끔 처리하는 예외적
  작업이라, 4주 일정 안에서 별도 UI를 만드는 비용을 아끼기로 함.
- 이어서 남은 항목 중 4개를 마저 확정: ⑥ 재고는 옵션 조합별 관리(`Product.stock`을 JSONB로 변경)
  ⑦ 결제는 Order와 1:N(재시도마다 새 Payment 레코드) ⑧ 크리에이터 중복 추천 등록 불가
  ⑨ Settlement.target_id는 단순 필드 조합(GenericForeignKey 미채택). 장바구니 중복 담기는 "상품+옵션+
  크리에이터가 모두 같을 때만 수량 증가"로 확정(크리에이터가 다르면 커미션 귀속이 달라지므로 별도 줄).
  근거는 `docs/decisions.md` ADR-016~020 참고.
- 크리에이터 회원가입 시 CreatorProfile 생성 시점은 "가입과 별도 단계로 프로필 작성"으로 확정. 여기에
  "벤더가 미리 지정한 크리에이터를 관리자가 대조 검증하는 절차"를 추가하고 싶다는 요구사항이 나와서
  구체화: 벤더가 알려준 크리에이터 핸들로, 관리자가 Django 관리자 사이트에서 `CreatorRecommendation`을
  직접 생성 — 크리에이터 검색 드롭다운이 이미 승인된 크리에이터만 보여주므로 이게 자동으로 검증 역할을
  겸함. 편의를 위해 상품의 벤더명도 같이 표시하도록 설정하기로 함. 근거는 `docs/decisions.md` ADR-022
  참고. (중간에 "관리자 사이트"라는 말을 우리가 만드는 `/admin` 페이지와 Django 기본 제공 관리자 화면,
  두 가지 뜻으로 섞어 써서 한 번 헷갈렸음 — 앞으로는 후자를 가리킬 땐 "Django 관리자 사이트"로 명확히
  구분해서 부르기로 함.)
- 이걸로 이번 설계 논의에서 나왔던 결정 사항은 모두 확정됨 (`docs/decisions.md` ADR-001~022).
- **스캐폴딩 진행**: `git init` + `.gitignore` 작성 후 백엔드·프론트엔드 뼈대 생성.
  - 백엔드: `backend/`에 venv 생성, Django/DRF/psycopg2/celery/redis/django-cors-headers/Pillow 설치
    (`requirements.txt`). `django-admin startproject config .` 후 스펙 6번 폴더 구조대로 8개 앱
    (`accounts`, `vendors`, `catalog`, `recommendations`, `orders`, `payments`, `settlements`,
    `adminconsole`) 생성. `docs/erd.md`에 정리해둔 필드·관계를 그대로 각 앱 `models.py`에 옮겨 작성함
    (빈 스텁이 아니라 실제 필드까지). `Cart`/`CartItem`은 별도 앱 없이 `orders` 앱에 같이 둠(주문
    흐름과 밀접해서). `settings.py`에 커스텀 User 모델(`AUTH_USER_MODEL`), PostgreSQL 연결(환경변수
    기반, `docker-compose.yml` 값과 매칭), DRF 세션 인증, CORS(로컬 Next.js 3000번 포트 허용)를 설정.
    ADR-022(벤더 지정 크리에이터를 Django 관리자 사이트에서 대리 등록 + 벤더명 표시)도 `admin.py`에
    반영.
  - **작업 중 이슈**: `ImageField`를 쓰려면 Pillow가 별도로 필요하다는 걸 `manage.py check`가 잡아줘서
    설치 추가. 또 `makemigrations`가 PostgreSQL에 실제로 연결을 시도하다가(Docker 미설치라 연결 불가)
    에러가 났는데, 모델 정의 자체가 맞는지 확인하려고 **일시적으로 SQLite로 바꿔서 마이그레이션 파일만
    생성**하고 다시 PostgreSQL 설정으로 되돌림 — 마이그레이션 파일 내용 자체는 DB 종류에 안 묶여있어서
    문제없음. 실제 `migrate` 실행은 Docker로 PostgreSQL을 띄운 뒤에 진행.
  - 프론트엔드: `npx create-next-app`으로 Next.js(TypeScript, Tailwind, App Router) 생성. 처음에
    `--src-dir` 옵션을 잘못 넣어서 `frontend/src/app/`으로 만들어졌길래, 스펙 6번 폴더 구조
    (`frontend/app/`, `components/`, `lib/` — src 없이)에 맞춰 `src/app`을 `app`으로 옮기고
    `tsconfig.json`의 경로 별칭도 수정. 스펙 7번에 정리해둔 6개 페이지 경로와 6개 공통 컴포넌트를
    최소 형태로 생성하고, `lib/api.ts`에 세션 쿠키 인증(ADR-011)을 고려한 fetch 래퍼 하나만 작성.
    `npm run build`로 전체 라우트가 정상 컴파일되는 것까지 확인함.

## 2026-09-09 — 2주차 마무리: 비주얼 다듬기 + 상품 상세 페이지

- 2주차가 끝났는지 다시 점검: 스펙 8번 목표(회원·크리에이터 승인, 카드형/카테고리 화면 UI) 자체는
  거의 다 됐지만, 상품 상세(`/products/[id]`)가 빈 껍데기였고 `ProductCard`가 클릭해도 아무 데도
  안 가는 상태라 "카드형 화면"이 실제로는 미완성이었음. 이 두 가지를 마저 채워서 2주차를 마무리하기로 함.
- **비주얼 개선(중간에 끼어든 작업)**: "카드가 하나도 안 들어가 있다"는 피드백을 처음엔 "카드가 렌더링
  안 된다(버그)"로 오해했는데, 실제로는 "화면이 안 예쁘다"는 디자인 피드백이었음 — 확인 차 서버 로그·
  HTML 응답을 다 뒤졌지만 문제없었던 이유. 이후:
  1. `globals.css`에 폰트가 Arial로 강제 지정돼 있어서 Next.js가 세팅해둔 Geist Sans 폰트가 적용조차
     안 되고 있던 걸 발견해 수정.
  2. 코랄 포인트 컬러(`--brand` CSS 변수) + 그라데이션 아바타/썸네일 + 상태별 색상 배지로 1차 개선.
  3. 사용자가 "그냥 흑백으로 가자"고 해서 `--brand` 값만 검정으로 바꿔 전체에 반영(색을 토큰 하나로
     관리해둔 덕분에 컴포넌트 코드는 거의 안 건드림). 상태 배지는 색 대신 짙기(확정=진한 검정, 진행중=
     중간 회색, 반려=옅은 아웃라인)로 의미를 구분하도록 재설계.
- **상품 상세 페이지**: 목업 데이터에 설명·옵션·추천 크리에이터 필드를 추가하고, 옵션/수량 선택은
  `product-actions.tsx`라는 별도 클라이언트 컴포넌트로 분리(페이지 자체는 서버 컴포넌트로 유지해 상품
  조회 로직만 담당). 장바구니 담기/바로구매 버튼은 3주차 연동 전까지 안내 메시지만 표시. `ProductCard`에
  `id`를 추가해 `/products/{id}`로 링크되게 함.
- **UI 실행 확인**: 매번 Playwright로 실제 클릭·폼 제출·옵션 선택까지 구동해서 스크린샷으로 검증 —
  이번엔 카테고리 페이지에서 카드 클릭 → 상세 페이지 이동 → 옵션 변경 → 수량 증가 → 담기 버튼까지
  전체 플로우를 한 번에 확인함. 존재하지 않는 상품 id 접근 시 안내 문구도 확인.
- `npm run build`/`lint`/`tsc --noEmit` 모두 통과. 3개 커밋(비주얼 1차, 흑백 전환, 상품 상세+카드
  연결)으로 나눠 GitHub에 push 완료.
- **2주차 마무리**: 스펙 8번 2주차 목표를 모두 목업 UI로 구현함. 다음은 Docker 설치 + `migrate`로
  1주차 뒷정리를 하거나, 3주차(장바구니·결제 연동, 정산 로직, 관리자 기능, 프론트-백엔드 API 연동)로

## 2026-09-14 — 시스템 구조 점검 + 벤더 승인 개념 재검토

- "지금 로그인 로직이 실제로 있냐"는 질문을 계기로 프론트-백엔드-DB-Redis/Celery-PortOne 연결 상태를
  한 장짜리 다이어그램으로 정리(Artifact로 게시). 실제로 동작하는 건 "브라우저 → Next.js"와
  "Next.js가 mock-data.ts를 그대로 렌더링"하는 것뿐이고, 그 뒤(Django API, DB, 비동기 작업, 결제)는
  전부 코드/설정만 있고 연결은 안 된 상태라는 걸 표로도 같이 정리함.
- 이어서 `/admin` 신청 심사 화면에 벤더가 크리에이터와 나란히 "승인 대상"으로 들어가 있는 게 이상하다는
  지적이 나옴. 짚어보니: `VendorProfile.status`(승인대기/승인/반려)를 실제로 확인하는 코드가 어디에도
  없고, 스펙 2.3상 벤더는 상품 상세의 배지로만 노출되기 때문에 승인 여부가 화면상 아무것도 바꾸지
  않음 — 승인 절차가 형식적이었던 것. 또한 벤더는 크리에이터처럼 스스로 "신청"하는 주체가 아니라
  관리자가 대신 등록하는 대상이라, 크리에이터와 같은 "신청 심사" 흐름에 넣는 것 자체가 개념적으로
  안 맞다는 게 핵심 지적이었음.
- 해결 방향(설계만 문서화, 구현은 보류): 벤더 전용 공개 프로필 페이지(`/vendors/{id}` — 이름·소개 +
  현재 공급 중인 상품 목록)를 새로 만들면, 그때는 `status`가 "이 벤더 프로필을 공개할지"를 실제로
  결정하는 의미 있는 게이트가 됨. 근거·필요 작업은 `docs/decisions.md` ADR-023, `docs/erd.md`
  VendorProfile, `docs/api-spec.md` "벤더 (제안, 구현 보류)" 섹션에 정리해둠. 지금 당장 구현하진 않고
  3주차 이후 우선순위 논의 때 다시 꺼내기로 함.

  4개 기능(신청 심사·상품 등록·배송 상태 변경·정산 승인) 전부 한 번에 하기로 확정. 새 `adminconsole`
  앱에 `IsAdmin` 권한 클래스(`User.role == "admin"`)와 4개 뷰를 구현 → ADR-026 참고.
  - **경로 충돌 발견**: `api-spec.md`에 관리자 콘솔 API가 전부 `/admin/...`으로 설계돼 있었는데,
    Django 기본 관리자 사이트가 이미 `/admin/`을 쓰고 있어서 그대로 두면 우리 API가 아예 호출되지
    않고 Django 관리자 사이트의 404로 가로채짐. Django 관리자 사이트를 `/django-admin/`으로
    옮겨서 해결 → ADR-025.
  - **배송 상태 변경 / 정산 승인은 대상 데이터가 아직 없는 문제**: 주문 생성 API·정산 배치 계산
    로직이 둘 다 4주차 스코프라 실제 데이터가 하나도 없었음. 화면을 눈으로 확인할 수 있게 데모 주문
    1건(`orders/migrations/0002_seed_demo_order.py`)과 데모 정산 대상 2건
    (`settlements/migrations/0002_seed_demo_settlements.py`)을 시드 데이터로 추가.
  - 테스트용으로 `createsuperuser`로 만들어뒀던 `admin@example.com` 계정의 `role`이 `buyer`로
    남아있던 걸 발견(`is_staff`/`is_superuser`와 서비스 코드가 쓰는 `role` 필드는 별개) —
    `accounts/migrations/0003_promote_dev_admin.py`로 `admin`으로 승격.
  - `/admin` 프론트엔드 페이지를 탭 4개(신청 심사/상품 등록/배송 상태 변경/정산 승인) 구조로 전면
    재작성, `mockApplications`를 걷어내고 `mock-data.ts` 자체를 삭제(더는 어디서도 안 씀). 로그인
    안 했거나 admin이 아니면 안내 문구만 보여주는 라우트 가드 추가(기존엔 없었음).
  - Playwright로 관리자 로그인 → 4개 탭 전부 데이터 로딩 확인 → 실제로 상품 등록 폼 제출, 배송 상태
    드롭다운 변경까지 브라우저에서 직접 조작해서 DB에 반영되는 것까지 확인.
- 이제 남은 목업 없이 `/admin`을 포함한 전체 화면이 실 API로 동작함. 다음 단계는 장바구니·주문·결제
  API(현재 완전히 비어있음)와 크리에이터 대시보드 API.
- 로그인 페이지도 손봄: admin 계정으로 로그인하면 바로 `/admin`으로 이동하도록 변경(원래는 역할 상관
  없이 항상 홈으로 보냈음).

## 2026-09-14 (계속 4) — 상품 간단 설명 분리 + 벤더 신청 심사 제외 + 벤더 판매 활성/중단 토글

## 2026-09-14 (계속 5) — 관리자 콘솔에서 상품 이미지 업로드

## 2026-09-14 (계속 7) — 장바구니 실 API 구현 + 크리에이터 계정 전체 흐름 실사용자 테스트

    상품 썸네일이 `/media/products/...`처럼 상대경로로 내려오는 걸 curl로 테스트하다가 발견(다른
    엔드포인트들은 DRF 제네릭 뷰가 자동으로 context를 넣어줘서 문제가 없었는데, 여긴 순수 APIView라

    것(ADR-020 규칙)까지 확인.
- "크리에이터 계정 만들어서 테스트해야 한다"는 요청으로, 기존 테스트 계정을 재사용하는 대신 완전히

  제한 확인 → 관리자 계정으로 실제 신청 심사 화면에서 승인 → 재로그인 → 헤더에 크리에이터 대시보드

  아님) 표시**까지 전체 파이프라인을 Playwright로 처음부터 끝까지 한 번에 돌려서 확인. 지난 며칠간
  만들어온 회원가입·크리에이터 프로필·관리자 승인·대시보드 기능이 실제로 이어서 동작하는 걸 확인한

- 이제 `/cart`·`/creator/dashboard` 둘 다 목업 없이 실 API로 동작하고, 남은 목업 화면은 없음. 다음
  단계는 주문·결제(PG 연동) — 이건 4주차 스코프.

## 2026-09-14 (계속 8) — 크리에이터 대시보드 미승인 화면 다듬기 + /creator/apply 재방문 버그 수정

  "니다."만 남는 어색한 개행이 있었음(코드만 보고는 못 잡아냈고 실제 렌더링을 봐야 보이는 문제였음).

- 지난번에 발견해둔 `/creator/apply` 재방문 버그를 고침 — 이 페이지가 `useAuth()`를 아예 안 쓰고
  있어서 이미 프로필이 있는 사람이 다시 들어와도 빈 폼을 그대로 보여줬던 문제. `user.creator_profile`

  승인이면 "이미 승인된 크리에이터입니다" + 대시보드 바로가기, 반려면 그 사실을 명확히 알려주는
  문구로 분리(더는 대기 중과 똑같은 문구가 아님). 겸사겸사 role 가드도 추가해서 buyer 계정이
  `/creator/apply`에 들어오면 안내 문구만 보이게 함(전에는 이것도 체크가 없었음).
  제출 성공 직후엔 `refresh()`를 호출해서 헤더·마이페이지 등 다른 곳의 크리에이터 상태도 새로고침
  없이 바로 최신 상태로 반영되게 함.
- Playwright로 신청 직후 → 같은 페이지 재방문(폼 안 뜨고 상태만) → 관리자 승인 → 재방문(승인 안내 +
  대시보드 링크) → buyer 계정으로 접근(차단) 네 가지 시나리오를 전부 새 계정으로 확인.

## 2026-09-14 (계속 12) — 주문 생성 API 구현 (이번 주 안에 결제까지 끝내야 함)

- "이제 뭐 해야 되냐"는 질문에 스펙 8번 일정표를 다시 확인해보니, 장바구니·결제(PG) 연동이 4주차가
  아니라 **3주차(이번 주) 스코프**였음을 정정 — 지난 devlog 여러 곳에 "4주차 예정"이라고 잘못
  적어놨던 것도 바로잡음. 이번 주 안에 완성해야 한다는 제약으로 주문 생성 API부터 착수.
- `Product.stock_key(option)` 메서드 추가 — 옵션 dict를 재고 JSON의 키 문자열로 바꾸는 실제 규칙이
  지금까지 코드에 없었음(ERD엔 "규칙을 정해서 고정"이라고만 적혀 있었음). options에 등록된 키 순서로
  값을 이어붙이는 것으로 고정.
- `POST/GET /orders`, `GET /orders/{id}` 구현. 장바구니와는 완전히 독립된 API로 만들어서(ADR-035),
  "장바구니에서 주문"과 "바로구매"가 같은 엔드포인트를 재사용함. 재고 검증·차감은 DB 트랜잭션
  (`select_for_update`)으로 원자적 처리 — 재고 부족한 상품이 하나라도 있으면 전체 주문을 거부하고
  아무것도 반영 안 함. curl로 정상 주문·재고 부족·잘못된 옵션 조합·타인 주문 조회 차단까지 전부 확인.
- 프론트: `/orders/[id]` 주문 상세/확인 페이지 신규, 장바구니 "주문하기" 버튼과 상품 상세 "바로구매"
  버튼을 실제 `POST /orders` 호출로 연결(주문 성공 후 장바구니 항목은 프론트가 직접 비움), 마이페이지
  "주문 내역은 추후 제공" 문구를 실제 주문 목록(`GET /orders`)으로 교체.
- Playwright로 상품 상세 → 장바구니 담기 → 장바구니에서 주문하기 → 주문 확인 화면 → 장바구니 자동
  비워짐 → 상품 상세에서 바로구매 → 마이페이지 주문 내역에 둘 다 뜨는 것까지 전체 흐름을 한 번에
  확인. 관리자 콘솔 "배송 상태 변경" 탭에도 새로 생긴 진짜 주문들이 바로 나타나는 것도 확인.
- **남은 문제(다음 단계로 이월)**: `OrderItem`이 생성되자마자 `paid`(결제완료) 상태로 시작함 —
  실제 결제 연동이 아직 없어서 임시로 이렇게 뒀는데, `OrderItem.Status`에 애초에 "결제 대기" 상태가
  없다는 설계 공백을 발견함(ADR-035). PG 연동 붙일 때 다시 짚어볼 부분.
- 버튼이 안 보인다는 보고를 받고 확인해보니 코드·서버는 정상이었음(curl로 직접 렌더링 확인) — 원인은
  (1) 테스트 중이던 장바구니가 이미 비어있어서 "주문하기" 버튼이 안 보인 것(빈 장바구니에선 원래
  버튼이 없고 "쇼핑하러 가기"만 나옴, 의도한 동작), (2) 브라우저에 예전 페이지가 캐시된 것으로 추정.
  실제 버그는 아니었음.
- "마이페이지가 텅 비어 보인다"는 피드백으로 위젯을 더 채움: 계정정보 카드 옆에 "총 주문"/"누적
  구매금액" 통계 카드(이미 불러온 주문 내역에서 계산, 별도 API 없음)를 추가하고, buyer 레이아웃 폭도
  `max-w-sm`(좁은 폼 스타일)에서 `max-w-2xl`(creator와 동일)로 넓힘. 스크린샷으로 확인하다가
  금액이 큰 통계값("147,000원")이 좁은 카드에서 "원"만 다음 줄로 밀리는 걸 발견해서, `StatCard`에
  `compact` prop을 추가해 이런 좁은 자리에서는 글자 크기를 줄이고 줄바꿈을 막도록 함.

## 2026-09-15 — 포트원(PortOne) 실 결제 연동 + 주문 취소/환불 기능

- 지난 devlog에서 이월했던 "결제 대기 상태 없음" 문제를 실제로 해결하는 단계. 테스트 키가 없어서
  결제 시뮬레이터로 대충 흉내만 낼지, 실제로 PG사에 가입해서 진짜 연동을 할지 물어봤고, 실제 가입
  쪽을 선택함.
- 취소/환불 기능을 처음엔 "스펙에 명시 안 돼 있다"는 이유로 스코프 밖이라고 판단했는데, 강한 반박을
  받음 — 결제 기능만 있고 취소가 없는 건 실서비스로서 말이 안 된다는 지적이 맞았고, 스펙에 없다는
  것만으로 뺀 건 내 판단 실수였음. 바로 인정하고 계획에 다시 포함시킴. 이후 "연동 시작 전에 구조를
  설명하고 허락을 받으라"는 요청에 따라, 코드를 쓰기 전에 모델 변경/백엔드 API/프론트 변경/명시적
  제외 범위(배송 시작 후엔 취소 불가, 부분 취소 없음, 반품 플로우는 별도 기능이라 이번엔 제외)를
  정리해서 먼저 확인받고 시작함.
- **PG사 키 값 혼선**: 사용자가 처음 준 키(`iamporttest_3`, `test_sk_...`, `test_ck_...`)가 실제론
  포트원 콘솔에서 "채널"을 설정할 때 쓰는 토스페이먼츠 채널 단 키였고, 연동 코드에 필요한 건 포트원
  레벨의 `storeId`/`channelKey`/API Secret이라는 걸 웹 검색으로 확인 → 정확한 위치(연동 관리 →
  [V2 API] 탭, 채널관리)를 안내해서 올바른 값 세 개를 다시 받음. API Secret은 코드나 커밋에 절대
  안 들어가게 루트 `.env`(gitignore 대상, docker-compose가 `${VAR}`로 주입)에만 저장.
- **백엔드**: `payments/portone.py`에 포트원 결제 조회(`GET /payments/{id}`)·취소(`POST
  /payments/{id}/cancel`) 래퍼 추가. `POST /payments/complete`는 프론트가 넘긴 `paymentId`를 그대로
  믿지 않고 포트원 서버에 직접 재조회해서 상태(`PAID`)와 금액이 일치할 때만 `OrderItem`을 `paid`로
  바꿈 — 프론트 응답은 조작될 수 있으니 유일하게 믿을 수 있는 건 PG사 서버뿐이라는 원칙. `POST
  /orders/{id}/cancel`은 포트원 쪽 결제 취소가 먼저 성공해야만 DB에서 재고 복원 + 상태 변경을 하도록
  구현(PG·DB 상태 불일치 방지). 취소 중 재고를 복원하려면 "어떤 옵션 조합을 얼마나 뺐는지" 알아야
  하는데 `OrderItem`에 그 정보(`option`)가 저장돼 있지 않다는 설계 공백을 발견해서 필드 추가.
- **프론트**: 포트원 브라우저 SDK를 `<script type="module">` 인라인으로 로드하고 "결제하기" 버튼에서
  `PortOne.requestPayment` 호출 → 성공하면 `/payments/complete` 호출 → 주문 상세 재조회. next/script의
  `onLoad` 콜백이 인라인 module 스크립트에는 아예 안 붙는 버그를 Playwright로 디버깅하다 발견(SDK 자체는
  정상 로드되는데 콜백만 안 불림) — `window.PortOne` 존재 여부를 직접 폴링하는 방식으로 우회.
- 전체 세부 설계와 이유는 [decisions.md](decisions.md) ADR-036, API 계약은 [api-spec.md](api-spec.md),
  스키마 변경은 [erd.md](erd.md)에 각각 반영.
- **검증 범위**: SDK 로딩, 결제창 렌더링(올바른 금액/상품명), 백엔드 인증(존재하지 않는 결제 ID 조회 시
  401이 아닌 404가 오는 것으로 인증 성공 확인), 검증/취소 로직은 모두 확인함. 다만 Playwright로 실제
  토스페이먼츠 샌드박스 결제창을 끝까지 밀어붙여서(카드사 선택 → 신한카드 프로모션 팝업 → 신한 VBV
  iframe → "다른결제" → "앱없이결제") 완주하려 했으나, 테스트 모드에서도 진짜 카드사 인증 UI가 그대로
  나오고 마지막에 휴대폰 인증(실제 SMS/ARS 발송 추정)을 요구해서 실제 전화번호 없이는 이 구간을 자동화로
  통과시키지 못함 — "성공 응답을 받은 이후의 서버 재검증 로직"은 코드 검토와 실패 케이스로 확인했지만,
  성공 케이스 전체 흐름의 엔드투엔드 완주는 못한 상태로 알려진 한계로 남겨둠.
- 관리자 콘솔 "배송 상태 변경" 탭도 정리: 이제 실 데이터에 `pending`(결제대기)/`cancelled`(취소됨)
  상태의 주문 항목도 나타날 수 있는데, 이 두 상태는 관리자가 드롭다운으로 임의로 못 바꾸게 막음 —
  `pending`은 아직 결제가 안 됐고 `cancelled`는 이미 PG 취소·재고 복원까지 끝난 상태라, 여기서 상태만
  바꾸면 실제 결제/재고 상태와 어긋나게 되기 때문(취소는 반드시 `POST /orders/{id}/cancel`을 거쳐야 함).

  "잘못된 값이 들어올 수 없는 경계"에서 막았어야 할 문제가 훨씬 뒤(실제 사용자 화면)에서 터진 것.
- 고친 것: (1) `AdminProductSerializer.validate_options`를 추가해서 각 옵션값이 문자열 배열인지
  서버에서 검증(아니면 예시와 함께 에러 반환), (2) 프론트 등록 폼도 제출 직전에 같은 검증을 한 번 더
  해서 API 왕복 없이 바로 알려주고, 옵션/재고 입력칸 라벨에 형식 예시를 추가, (3) 이미 잘못 저장된
  테스트 상품(#13)의 `options`를 `{}`로 직접 수정해서 크래시 제거. Django shell로
  `AdminProductSerializer`에 잘못된 모양(`{"블랙": 0}`)과 올바른 모양(`{"색상": ["블랙","화이트"]}`)을
  각각 넣어서 검증이 의도대로 동작하는 것 확인.

  같은 방식으로 테스트해서 `OrderItem.creator_id=1`, `commission_amount=1950`으로 정상 계산되는 것
  확인. Django shell로 크리에이터 1의 전체 주문 항목(결제대기/결제완료/상품준비/취소됨 섞인 상태)에
  대한 대시보드 집계도 다시 계산해서, 어제 고친 로직대로 결제대기·취소된 건은 정확히 제외되고 나머지만
  잡히는 것까지 확인 — 어제 고친 대시보드 집계 로직과 오늘 고친 귀속 로직이 서로 맞물려 정상 동작함.
- 남은 한계는 ADR-037에 정리: 이 링크 방식은 "진짜 그 링크를 거쳐 왔는지"까지는 증명 못 한다(실제
  어소시에이트 프로그램들도 같은 한계를 그냥 신뢰 기반으로 감수함). 막아야 했던 건 "관계 없는
  크리에이터에게 커미션이 새는 것"이었고 그건 어제·오늘 수정으로 막혔음.

## 2026-09-17 — 4주차 남은 항목 점검 + 정산 생성 기능 구현

- "이제 뭐 남았냐"는 질문에 스펙 8번 일정표를 다시 확인 — 1~3주차는 전부 끝났고 지금은 4주차
  ("통합 테스트·발표 준비") 구간. 남은 걸 정리하다가, "정산 승인" 화면 숫자가 전부 개발 초반에 심어둔
  가짜 데이터(`0002_seed_demo_settlements.py`)이고, 실제 주문 데이터로 정산 금액을 계산하는 로직은
  스펙에서 "Celery 배치가 한다"고만 가정해뒀을 뿐 한 줄도 없다는 걸 다시 짚음 — Celery 워커 자체가
  docker-compose에 없었음.
- 세 가지 선택지(① 스펙대로 Celery 자동 배치, ② 관리자가 버튼 누르면 그 자리에서 실제 데이터로 계산,
  ③ 지금처럼 데모 데이터 유지)를 정리해서 설명 → 사용자가 "Celery를 쓰는 거냐"고 재차 확인 → Celery가
  왜 필요한 도구인지(자동 주기 실행 / 오래 걸리는 작업 분리)와 이번 케이스엔 둘 다 해당 안 된다는 걸
  설명 → ②(버튼 클릭 시 동기 계산)로 결정.
- `OrderItem.settled_at`(정산 포함 시각, nullable) 필드 추가 — 정산 생성을 여러 번 눌러도 같은 배송완료
  건이 중복으로 정산되지 않게 막는 용도. 이 필드가 없다는 걸 설계 중에 발견함(ADR-036의 `option` 필드
  추가와 같은 패턴 — "나중에야 필요하다는 걸 알게 된 추적용 필드").
- `POST /admin/settlements/generate` 구현 — 배송완료 & 미정산 항목을 크리에이터별/벤더별로 묶어서
  각각 `Settlement`를 생성. 정산 승인 탭에 "정산 생성" 버튼 추가.
- curl + Django shell로 검증: 배송완료 항목 2건(크리에이터 2명, 벤더 2곳)으로 정산 4건이 정확한 금액
  (예: 벤더 몫 = 단가×수량 − 커미션)으로 생성되는 것, 재실행 시 이미 정산된 항목은 다시 안 잡혀서
  `created: 0`이 오는 것, 크리에이터 없이(추천 없이) 산 주문은 벤더 몫만 정산되고 크리에이터 쪽엔
  아예 안 잡히는 것까지 확인. 실제 관리자 콘솔 화면에서 버튼 클릭 → 새 정산행 추가 → 승인까지 실제
  UI로도 확인.
- 중간에 테스트 스크립트를 동시에 두 개 돌리다가 "생성 버튼 눌렀는데 메시지가 이상하다"고 순간
  착각했는데, 확인해보니 앞서 실행 중이던(타임아웃으로 백그라운드로 넘어간) 다른 테스트 스크립트가
  이미 그 버튼을 눌러서 정산을 만들어놓은 상태였던 것 — 실제 버그 아니었음(테스트 스크립트끼리
  겹쳐서 생긴 착시).
- 이 작업 도중 Docker Desktop과 프론트 dev 서버가 두 번 더 죽어서(재부팅 등으로 추정) 그때마다
  재기동. 관리자 콘솔을 실제 로그인해서 테스트해야 해서 admin 계정 비밀번호를 알고 있는 값

## 2026-09-17 (계속) — 회원가입에 이메일 인증 추가

- 사용자가 이메일 중복확인 → 인증번호 발송/확인 → 인증 완료 전엔 가입 자체를 막는 흐름을 구체적으로
  요청(API 이름까지 제안: `check-email`/`send-verification-code`/`verify-code`), Gmail SMTP 계정·앱
  비밀번호도 같이 줌. 코드 짜기 전에 계획부터 보여달라고 해서, Redis 저장 방식·API 3개·프론트 흐름·
  재발송 쿨다운(60초)·시도 제한(5회) 여부를 정리해서 먼저 확인받고 시작.
- Redis를 이번에 처음 실사용함 — `requirements.txt`에 `redis` 패키지, `docker-compose.yml`에 Redis
  컨테이너와 연결 정보는 전부터 있었는데 실제로 쓰는 코드가 하나도 없었음(정산 배치를 Celery로
  만들려다 어제 동기 처리로 단순화하면서 결국 못 씀). 인증코드처럼 "몇 분 뒤 자동 소멸"이 필요한
  값이 Redis TTL과 딱 맞아서, `django-redis` 없이 `redis` 클라이언트로 직접 연결(캐시 프레임워크
  전체가 필요한 게 아니라 값 저장·조회·만료만 필요해서 더 단순한 쪽을 택함).
- `accounts/verification.py`에 로직 정리: 코드 5분 TTL, 인증완료 표시 30분 TTL, 재발송 60초 쿨다운,
  틀린 시도 5회 제한(초과 시 코드 무효화). `POST /auth/signup`은 `SignupSerializer.validate_email`에서
  Redis의 인증완료 표시를 최종 확인 — 이 절차를 건너뛰고 API를 직접 호출해도 막힘.
- SMTP 자격증명은 포트원 때(ADR-036)와 같은 방식으로 루트 `.env`에만 저장, 코드/커밋에는 안 남김.
- curl로 백엔드 로직 전부 검증(중복확인, 코드발송, 오답 카운트 1~5회, 재발송 쿨다운 거부, 정답 확인,
  미인증 상태 가입 거부). **실제로 사용자 본인 이메일(발신 계정과 동일)로 진짜 인증 메일을 보내서**
  Redis에 저장된 코드로 가입까지 성공하는 걸 확인(테스트 후 계정 삭제 — 자기 자신에게 보내는 거라
  안전한 테스트였음).
- 프론트 회원가입 폼을 다단계로 재작성: 이메일 입력 → 중복확인 버튼 → (사용 가능하면) 인증번호 받기
  버튼 → 코드 입력창(5분 카운트다운 표시) + 확인 버튼 → 인증 완료 뱃지 → 그제서야 비밀번호/이름/역할
  필드가 활성화되고 가입 버튼도 눌림. 이메일을 인증 후 다시 바꾸면 인증 상태 전부 초기화.
- Playwright로 실제 브라우저에서 전체 흐름 완주: 이메일 입력 → 중복확인 → 인증번호 받기 → (테스트
  편의상 Redis에서 실제 발송된 코드를 직접 조회) → 코드 입력 → 확인 → 나머지 필드 입력 → 가입 완료
  → 자동 로그인까지 확인. 도중에 테스트 스크립트의 `button:has-text("확인")` 셀렉터가 "확인"과
  "중복확인" 버튼을 둘 다 매칭해서(부분 문자열 매칭이라) 엉뚱한 버튼을 누르는 바람에 인증이 전혀
  안 되는 것처럼 보였던 순간이 있었음 — 실제 앱 버그가 아니라 테스트 스크립트의 셀렉터 문제였고,
  정확한 버튼을 지정하는 셀렉터(`exact: true`)로 바꾸니 정상 확인됨. 중복 이메일이면 인증번호 받기
  버튼 자체가 안 뜨는 것도 확인.
